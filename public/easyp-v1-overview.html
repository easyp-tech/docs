EasyP v1.0 · Pilot

Контракты в Git.
Один путь до кода.

Модульные Protobuf-схемы, фиксированные зависимости, генерация через плагины и проверки API теперь собраны в последовательный workflow. Источник версий — protobuf.mod, воспроизводимость — protobuf.lock.

01 / Модель

От исходника до результата

Каждый шаг использует явно выбранные модули и корни исходников. Изменения версий проходят через менеджер зависимостей, а не через конфиг плагина.

Рабочая цепочка v1.0
01 — DECLARE

protobuf.mod

Идентичность модуля, roots, прямые и транзитивные Git-зависимости.

02 — LOCK

protobuf.lock

Выбранный коммит и h1-хеш для каждого внешнего модуля.

03 — SELECT

easyp.gen.yaml

Какие модули генерировать, какими плагинами и куда писать файлы.

04 — VERIFY

Код + проверки

Генерация, lint, breaking, validate-config и CI из одних источников.

easyp.yaml задаёт правила линтинга и breaking checks рядом с proto-схемами; потребитель может иметь свой easyp.gen.yaml рядом с приложением.
02 / Конфигурация

Четыре файла — четыре задачи

В v1.0 больше не нужно смешивать зависимости, плагины и проверки в одном YAML.

protobuf.mod

Текстовый манифест модуля. Roots считаются относительно каталога самого файла. Поддерживает require и локальный replace.

modulerootsrequirereplace

protobuf.lock

Создаётся командами EasyP. Сохраняет выбранные версии, точные Git-коммиты и h1-хеши. Редактировать вручную не нужно.

version: 1commithash: h1:…

easyp.gen.yaml

Конфиг потребителя: выбор модулей, локальные/встроенные/удалённые плагины, опции и managed mode.

generate.modulespluginsmanaged

easyp.yaml

Конфиг продюсера: пресеты и правила lint, исключения и Git-baseline для проверки совместимости.

lintersissuesbreaking
03 / Показываем на примере

Один инструмент, три масштаба

Переключайте сценарии: обычный проект, монорепозиторий с вложенными модулями и проект без внешних зависимостей.

Контракты как отдельный Git-модуль

Манифест описывает источник proto, генератор выбирает модуль и плагины, политика остаётся рядом со схемами.

основной путь
protobuf.mod
module github.com/acme/contracts
roots proto

require github.com/acme/shared v1.2.3
easyp.gen.yaml
version: v1
generate:
  modules: [github.com/acme/contracts]
plugins:
  - name: go
    out: gen/go
    opts:
      paths: source_relative
  - name: go-grpc
    out: gen/go
    opts:
      paths: source_relative
easyp.yaml
version: v1
linters:
  default: STANDARD
breaking:
  baseline: git:main
Команды
easyp mod tidy
easyp mod download
easyp generate
easyp lint --path proto
easyp breaking --path proto --against main

Два модуля в одном Git-репозитории

Каждый вложенный модуль объявляется отдельным require. Отдельные теги не нужны: требование без версии разрешается по Git HEAD и фиксируется в lock.

monorepo
Репозиторий contracts
contracts/
├── foo/
│   ├── protobuf.mod
│   └── schemas/proto/user/v1/foo.proto
└── bar/
    ├── protobuf.mod
    └── schemas/proto/order/v1/bar.proto

# В каждом модуле roots schemas/proto
protobuf.mod потребителя
module github.com/acme/app

require (
  github.com/acme/contracts/foo
  github.com/acme/contracts/bar
)
Разрешение путей
Физический файл: contracts/foo/schemas/proto/user/v1/foo.proto
Proto import:      user/v1/foo.proto

Физический файл: contracts/bar/schemas/proto/order/v1/bar.proto
Proto import:      order/v1/bar.proto

После easyp mod tidy появятся две записи lock. Каждый модуль имеет собственный roots относительно своего protobuf.mod. EasyP добавляет путь к вложенному модулю для поиска файла, а import path считает уже относительно root.

Проект без protobuf.mod

Если Git-зависимостей нет, манифест не обязателен: каталог проекта становится локальным root для генерации и списка proto-файлов.

минимальный старт
Структура
project/
├── api/v1/user.proto
├── easyp.gen.yaml
└── easyp.yaml

# protobuf.mod и protobuf.lock отсутствуют
easyp.gen.yaml
version: v1
plugins:
  - name: python
    out: gen/python
Команды
easyp generate
easyp ls-files --include-imports=false

Когда появятся внешние импорты, добавьте protobuf.mod и требуемые модули через easyp get.

04 / Git-зависимости

Точно закрепить. Легко обновить.

Версия может быть SemVer-тегом, полным коммитом или отсутствовать. В последнем случае EasyP выбирает HEAD и записывает точный коммит в lock.

get

Добавить модуль

easyp get module[@version|@commit] добавляет прямой require. Найденные транзитивные зависимости записываются с // indirect.

tidy

Собрать граф

mod tidy разрешает требования и обновляет lock. Неразрешённый импорт не превращается в ложный пустой lock.

h1

Проверить байты

mod download берёт точные коммиты из lock и проверяет h1-хеш содержимого, включая повторное использование кеша.

↻

Обновить управляемо

mod update обновляет совместимые версии по тегам и требования без версии до HEAD; явно закреплённый коммит сохраняет выбор.

↧

Положить рядом

mod vendor копирует proto-файлы из lock в easyp_vendor. Повторяющиеся import path вызывают ошибку.

↔

Читать чужие форматы

Git-зависимость может описывать roots через Buf v1/v2 или старый EasyP. Потребителю достаточно собственного v1-манифеста.

Как находится модуль

У каждого вложенного protobuf.mod своя identity и roots. EasyP читает метаданные зависимости в её каталоге; если подходящего конфига нет, источником считается корень репозитория.

Локальная разработка

replace module => ../local-copy помогает при генерации и lint. Перед записью воспроизводимого lock через get, tidy или update локальную замену нужно убрать.

05 / Генерация

Один выбор модулей, любые выходы

easyp generate обнаруживает consumer-конфиги, компилирует выбранные модули целиком и запускает плагины. Версии proto-зависимостей не дублируются в YAML генератора.

01

Локальные и WASM

plugins[].name выбирает локальный protoc-gen-* или встроенный WASM-плагин через существующий resolver. Можно задать несколько плагинов и разные out.

02

Бинарь по пути

plugins[].path запускает конкретный исполняемый файл. Относительный путь считается от каталога запуска easyp generate.

03

Своя команда

plugins[].command принимает список из программы и аргументов, например [sh, ./tools/plugin.sh]. Это поле называлось command и в старом конфиге.

04

Удалённые плагины

plugins[].remote подключает удалённый генератор. Отдельное поле version требует зафиксированный SemVer; эта версия передаётся исполнителю.

05

Managed mode

generate.managed сохраняет правила disable/override для file и field options с селекторами module, package, path и field.

06

Go package prefix

options.go.package_prefix вычисляет Go-импорты без редактирования proto. Корневой generator может дать вложенным значение по умолчанию.

07

Несколько потребителей

У каждого сервиса может быть свой easyp.gen.yaml. --project запускает один выбранный consumer. Plugins не наследуются из корня.

08

Descriptor set

--descriptor_set_out пишет набор дескрипторов; --include_imports добавляет транзитивные импорты. Результат можно использовать в других инструментах.

easyp.gen.yaml · явный бинарь и своя команда
version: v1
plugins:
  - path: ./tools/protoc-gen-custom
    out: ./gen/custom
  - command: [sh, ./tools/protoc-plugin.sh]
    out: ./gen/script

Для каждого плагина указывается один источник: name, path, command или remote. Собственный плагин читает CodeGeneratorRequest из stdin и пишет CodeGeneratorResponse в stdout.

Конфиг генератора сначала использует protobuf.mod рядом с собой; если его нет — корневой манифест проекта. Зависимости выбранного модуля берутся оттуда же.
06 / Политики

Схемы под контролем

Одни и те же proto-файлы можно проверять локально и в CI. Политики действуют по дереву каталогов, а breaking сравнивает API с Git baseline.

Lint

Пресеты MINIMAL, BASIC, STANDARD, COMMENTS; выборочные enable/disable и настройки отдельных правил. Ближайший easyp.yaml задаёт секцию для своего поддерева. Исключение без path может подавить выбранные правила.

Breaking

breaking.baseline: git:main выбирает Git-ветку для существующего checker. Вложенная политика может выбрать другой baseline; breaking.ignore исключает указанные пути.

easyp.yaml · пример политики
version: v1
linters:
  default: STANDARD
  enable: [RPC_REQUEST_RESPONSE_UNIQUE]
  disable: [PACKAGE_VERSION_SUFFIX]
issues:
  exclude-rules:
    - linters: [FIELD_LOWER_SNAKE_CASE]
breaking:
  baseline: git:main
07 / Опыт разработчика

Проверить раньше, понять быстрее

✓

validate-config

Рекурсивно проверяет все четыре типа файлов. Можно указать один файл или каталог; JSON-ошибки содержат путь, ошибки структуры YAML — строку и столбец.

{ }

schema-gen

Генерирует отдельные JSON Schema для easyp.yaml, easyp.gen.yaml и protobuf.lock. YAML-валидация CLI использует тот же источник схемы.

AI

MCP для конфига

Экспортируемый Go-пакет mcp/easypconfig регистрирует easyp_config_describe в своём MCP-сервере. Инструмент описывает редактируемые YAML-файлы.

$

Переменные окружения

В двух YAML-конфигах работают ${NAME}, ${NAME:-default} и экранирование $${NAME}. Комментарии YAML подстановке не мешают.

ls

ls-files

Показывает локальные proto и доступные импорты из зависимостей и встроенных схем. --include-imports=false оставляет только локальные файлы.

⚙

init и completion

init создаёт стартовые v1-файлы, умеет выводить identity из Git origin и учитывает подтверждение перезаписи. completion помогает работать из shell.

09 / Честный статус пилота

Что пока оставлено на потом

Эти ограничения отмечены явно: конфиг не должен молча создавать впечатление, что неподдерживаемая настройка сработала.

generate.packagesФильтрация Protobuf-пакетов зарезервирована. Непустое значение сейчас вызывает ошибку; генерация выбирает целые модули.
Buf Registry → GitАвтоматического преобразования имени зависимости Buf Registry в Git-источник нет. Git-модуль объявляют явно.
Расширенные breaking-политикиcategories, ignore_unstable: true и extends не включены в текущий checker и вызывают ошибку.
Явное extends и glob-исключенияlinters.extends и issues.exclude-rules.path пока не реализованы; исключения без path работают.
Фильтры корней BufБуферные include/exclude-фильтры для Git-зависимостей не перенесены; при их наличии EasyP сообщает об ошибке.
MCP scopeeasyp_config_describe объясняет только редактируемые YAML-файлы. protobuf.mod и protobuf.lock остаются за CLI.

Что показать в живой демонстрации

Откройте вкладку «Несколько модулей», выполните easyp mod tidy, затем easyp ls-files и easyp generate. Коллеги увидят отдельные записи lock для вложенных модулей и import path без префикса каталога модуля.
