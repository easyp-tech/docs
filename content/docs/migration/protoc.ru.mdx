---
title: "Переход с protoc на EasyP v1"
---

Это ручное сопоставление существующих исходников, плагинов и правил с v1. Команда <code>easyp migrate</code> принимает конфигурацию EasyP v0, а не произвольные скрипты или конфигурацию другого инструмента. Сохраните исходные файлы и результаты прежней генерации для сравнения.

## Модуль и исходники

<code>protobuf.mod</code>:

~~~text
module github.com/acme/contracts
roots proto
~~~

Путь <code>proto/hello/v1/hello.proto</code> имеет import-имя <code>hello/v1/hello.proto</code>. Если прежний запуск выбирал только часть корня, не переносите его механически на весь модуль: v1 генерирует целые выбранные модули.

## Генерация

<code>easyp.gen.yaml</code>:

~~~yaml
version: v1
plugins:
  - name: go
    out: gen/go
    opts: [paths=source_relative]
  - name: go-grpc
    out: gen/go
    opts: [paths=source_relative]
~~~

Зафиксируйте версии используемых исполняемых плагинов в окружении. Сохраните прежние <code>go_package</code> и согласуйте их с физическим output. При необходимости генерировать также импорты включите <code>with_imports: true</code> у конкретного плагина. Это не параметр descriptor export.

## Политика проверок

<code>easyp.yaml</code>:

~~~yaml
version: v1
linters:
  default: BASIC
breaking:
  baseline: git:main
  categories: [FILE]
~~~

Сопоставляйте отдельные правила по фактическим именам и результатам; одинаковые названия пресетов разных инструментов не доказывают эквивалентность. <code>breaking.ignore</code> содержит пути, а не имена правил.

## Зависимости и проверка результата

Объявите внешние зависимости через <code>easyp get</code> или <code>require</code> в manifest. Git-источник нельзя однозначно угадать по произвольному proto-import. Для первоначального разрешения выполните <code>mod tidy</code> и закоммитьте lock; в последующих проверках используйте <code>mod download</code>, а не обновление версий.

~~~bash
easyp validate-config
easyp mod tidy
easyp lint
easyp breaking --against main
easyp generate
~~~

Указанный baseline должен быть доступен локально. Сравните с прежней генерацией имена файлов, import paths и содержимое, затем соберите и протестируйте потребляющий проект. Не удаляйте прежние скрипты до этого сравнения. Для нескольких проектов используйте повторяемый <code>--project</code> или явно разрешённый <code>--all</code>.

Если исходный проект уже использует EasyP v0, начните с [предварительного просмотра миграции](/docs/migration/easyp-v0).
