Запускайте проверку зависимостей, линтинг, breaking-проверки и генерацию отдельными шагами: так ошибка укажет на этап, требующий внимания.

## Предварительные требования и инструменты

Пример предполагает корневые <code>protobuf.mod</code> и закоммиченный <code>protobuf.lock</code>, корневой <code>easyp.yaml</code>, схемы в <code>proto</code> и корневой <code>easyp.gen.yaml</code>, записывающий отслеживаемые файлы в <code>gen</code>.

Workflow использует подготовленный self-hosted Linux runner с пользовательской меткой <code>easyp-v1</code>. Назначайте её после подготовки выбранного бинарника EasyP с поддержкой v1 и необходимых локальных плагинов в <code>PATH</code>. Для hosted runner добавьте принятую в проекте установку фиксированных версий инструментов до шагов EasyP. Пример не предполагает существования конкретного опубликованного артефакта релиза v1.

Локальные и встроенные плагины не принимают фиксацию через YAML-поле <code>version</code>: их версии определяются установленными исполняемыми файлами и бинарником EasyP. Удалённым плагинам нужна отдельная фиксированная семантическая <code>version</code> в <code>easyp.gen.yaml</code>.

## Workflow для Pull Request

~~~yaml
name: protobuf-ci

on:
  pull_request:

permissions:
  contents: read

jobs:
  verify:
    runs-on: [self-hosted, linux, x64, easyp-v1]
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Verify toolchain
        run: easyp --version

      - name: Verify locked dependencies
        run: easyp mod download

      - name: Lint schemas
        run: easyp lint --path proto

      - name: Check compatibility
        env:
          BASE_REF: ${{ github.event.pull_request.base.sha }}
        run: easyp breaking --path proto --against "$BASE_REF"

      - name: Generate code
        run: easyp generate --project .

      - name: Check committed generated files
        run: |
          git diff --exit-code -- gen
          test -z "$(git ls-files --others --exclude-standard -- gen)"
~~~

Последний шаг обнаруживает изменения отслеживаемых файлов и новые неотслеживаемые файлы в <code>gen</code>. Адаптируйте пути под проект; игнорируемые сгенерированные файлы эта проверка не охватывает. После генерации также запускайте обычные тесты потребителей.

## Политики линтинга и совместимости

Простой корневой <code>easyp.yaml</code>:

~~~yaml
version: v1
linters:
  default: STANDARD
breaking:
  baseline: git:main
  categories: [FILE]
  ignore_unstable: false
  ignore: [proto/experimental]
~~~

Явный <code>--against</code> из workflow заменяет эту базу SHA базового коммита PR. Передавайте ссылку напрямую, без <code>git-ref=</code> и <code>git:</code> во флаге. Поддерживаются ветки, лёгкие и аннотированные теги, полные SHA и разрешимые локально Git-ревизии; необходимые ссылки и объекты должны присутствовать локально. Короткое имя ветки приоритетнее одноимённого тега.

Для сравнения релиза явно выберите существующий тег:

~~~bash
easyp breaking --path proto --against refs/tags/v1.2.0
~~~

Выбирайте нужный предыдущий релиз явно: порядок создания тегов не обязательно задаёт историю совместимости. Каждая ревизия использует свои манифесты модулей, lock-файлы и зависимости, поэтому breaking-проверка может загрузить зависимости, которые не нужны текущему checkout.

<code>FILE</code> — единственная поддерживаемая дополнительная категория. <code>ignore_unstable</code> работает для поддерживаемых суффиксов пакетов. Пути исключений отсчитываются от файла политики с секцией <code>breaking</code>: здесь <code>proto/experimental</code> задан относительно корневой политики. Вложенные секции заменяют секции целиком; непустое <code>extends</code> не поддерживается.

## Выбор проектов генерации

Для файлов генератора бэкенда и фронтенда используйте:

~~~bash
easyp generate --project ./backend --project ./frontend
~~~

Для явного рекурсивного выбора используйте <code>easyp generate --all</code>. Обычный <code>easyp generate</code> выбирает ближайший вышестоящий файл генератора. Сочетать <code>--project</code> и <code>--all</code> нельзя.

Чтобы разделить генерацию на matrix jobs, задайте в матрице каталоги проектов и передавайте выбранный каталог в <code>--project</code>. Каждой job нужны соответствующие плагины и проверки вывода; одни имена языков не выбирают конфигурацию генерации.

## Кеш зависимостей и приватные источники

Зависимости задаются в <code>protobuf.mod</code>, выбранные коммиты и хеши — в <code>protobuf.lock</code>. <code>easyp mod download</code> проверяет lock, не обновляя его. Обновляйте зависимости в отдельном проверяемом изменении до проверочной job.

По умолчанию хранилище EasyP находится в <code>~/.easyp</code>; его можно перенести через <code>EASYPPATH</code>. Если кешируете его, включайте в ключ кеша ОС, версию инструментов EasyP и хеши нужных lock-файлов. Восстановленный кеш — оптимизация, проверка зависимостей всё равно выполняется.

До шага зависимостей настройте Git-аутентификацию, необходимую приватным источникам. Храните учётные данные в принятом для runner механизме секретов и не выводите их в логи. Локальная замена не устраняет загрузки, если весь граф зависимостей не локальный и не находится в проверенном кеше; удалённым плагинам всё ещё нужна сеть. <code>tidy</code> и <code>update</code> отклоняют активные локальные замены и не являются проверками только для чтения.

## Отладка

| Симптом | Что проверить |
| --- | --- |
| База не разрешается | Получите нужную ссылку и объекты через полную историю или явный fetch. |
| Неизвестное поле политики или правило | Согласуйте конфигурацию с установленным бинарником v1 и поддерживаемой схемой. |
| Плагин отсутствует или вывод отличается | Проверьте исполняемый файл, выбранный из PATH, и фиксированные версии инструментов. |
| Проверка зависимостей падает | Проверьте закоммиченные манифест и lock, доступ к источникам и сообщение о несовпадении хеша. |
| Проверка сгенерированных файлов падает | Повторите генерацию с теми же проектами и инструментами, проверьте diff и закоммитьте нужные изменения. |

Для диагностики сохраняйте <code>easyp --version</code>, упавшую команду и нужную Git-ссылку. См. [breaking-проверки в CI](/ru/docs/guides/breaking-checks-ci) и [воспроизводимость сборок](/ru/docs/guides/reproducibility).
