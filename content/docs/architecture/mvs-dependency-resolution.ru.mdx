В качестве основного алгоритма разрешения зависимостей для Protocol Buffer модулей EasyP использует **Minimal Version Selection (MVS)**. Разработанный Рассом Коксом (Russ Cox) для модулей Go, MVS отличается от традиционных пакетных менеджеров (таких как Cargo или npm) тем, что выбирает *минимальную* (самую старую из удовлетворяющих) явно объявленную версию, вместо сложного поиска компромиссов через SAT-солверы или автоматического обновления до `latest`.

В данном документе подробно рассматриваются алгоритм MVS, его поведение при разрешении ромбовидных зависимостей (diamond dependencies), DSL файла `protobuf.mod`, устройство `protobuf.lock` и сравнение с альтернативными моделями.

---

## 1. Концепция Minimal Version Selection (MVS)

Традиционные алгоритмы разрешения зависимостей (например, PubGrub в Cargo или стратегия Max Version в npm) рассматривают выбор версий как задачу удовлетворения ограничений (CSP), решаемую с помощью NP-полных SAT-солверов или агрессивного подтягивания свежих версий. В отличие от них, MVS в EasyP ориентирован на предсказуемость, детерминированность и независимость от состояния удалённых реестров.

### Почему EasyP выбирает MVS

| Проблема при работе с Proto | Подход Buf v2 / Традиционный | Подход EasyP MVS |
| --- | --- | --- |
| **Рассинхрон версий («diamond»)** | Резолюция на весь workspace целиком: единая версия пакета на всех потребителей, конфликты между командами разруливаются вручную. | Per-module (помодульная) резолюция. Каждый модуль резолвит свои зависимости независимо. |
| **Зависимость от состояния реестра** | Стратегия `latest` или изменения в реестре могут неявно изменить результат повторной сборки. | Детерминированный выбор `max(запрошенных минимумов)`. Без SAT-солвера и обращения к реестру при наличии lock. |
| **Коллизии Proto-схем** | Несколько мажорных/минорных версий в одном proto-root ломают уникальность FQN. | Ровно одна версия каждой зависимости в графе модуля, строго зафиксированная в `protobuf.lock`. |

### Базовые принципы алгоритма

1. **Явные нижние границы версий**: Каждая зависимость в `protobuf.mod` указывает конкретную базовую версию (например, `github.com/acme/weather v1.2.0`). Эта версия рассматривается как *минимально необходимая requirement*, а не диапазоновое ограничение.
2. **Максимум из минимумов**: Если несколько модулей в графе требуют разные минимальные версии одной и той же зависимости, MVS выбирает **максимальную** из запрошенных минимальных версий.
3. **Детерминизм High-Water Mark**: Выбранная версия гарантированно удовлетворяет всем объявленным минимальным требованиям без возвратов (backtracking) и неожиданных мажорных обновлений.

## 2. Пошаговый разбор разрешения ромбовидных зависимостей (Diamond Dependency)

Классическая проблема управления зависимостями — ромбовидная зависимость. Рассмотрим случай, когда корневой модуль `user` напрямую зависит от `common` и `weather`, а `weather` транзитивно требует более новую версию `common`.

### Структура графа

```text
               +-------------------+
               |    proto/user     | (Корневой модуль)
               +---------+---------+
                         |
           +-------------+-------------+
           |                           |
           v                           v
+---------------------+     +---------------------+
| github.com/acme/    |     | github.com/acme/    |
| common v1.2.0       |     | weather v2.1.0      |
+---------------------+     +----------+----------+
                                       |
                                       v
                            +---------------------+
                            | github.com/acme/    |
                            | common v1.3.0       |
                            +---------------------+
```

### Пошаговый алгоритм MVS

<Tabs items={["Шаг 1: Обход графа", "Шаг 2: Сбор требований", "Шаг 3: Выбор максимума", "Шаг 4: Фиксация в Lock"]}>
  <Tab value="Шаг 1: Обход графа">
    EasyP начинает с чтения `protobuf.mod` корневого модуля (`proto/user/protobuf.mod`) и рекурсивно обходит все транзитивные `require`:
    - Корень `user` требует `github.com/acme/common v1.2.0`.
    - Корень `user` требует `github.com/acme/weather v2.1.0`.
    - Обход читает `protobuf.mod` зависимости `github.com/acme/weather v2.1.0` и находит требование `github.com/acme/common v1.3.0`.
  </Tab>
  <Tab value="Шаг 2: Сбор требований">
    Алгоритм формирует список всех запрошенных минимальных версий для каждого уникального URL модуля:
    - Модуль: `github.com/acme/common`
    - Запрошенные минимумы: `[ v1.2.0 (от user), v1.3.0 (от weather) ]`
  </Tab>
  <Tab value="Шаг 3: Выбор максимума">
    MVS сравнивает запрошенные минимальные версии по правилам SemVer:
    `Итоговая версия = max(v1.2.0, v1.3.0) = v1.3.0`
    Поскольку `v1.3.0` обратимо совместима с `v1.2.0`, выбор `v1.3.0` удовлетворяет требованиям и `user`, и `weather`.
  </Tab>
  <Tab value="Шаг 4: Фиксация в Lock">
    Итоговый набор версий (`common v1.3.0`, `weather v2.1.0`) записывается в `protobuf.lock` вместе с хешами коммитов и контрольными суммами содержимого.
  </Tab>
</Tabs>

### Изоляция версий per-module

В отличие от единого резолвера на весь workspace, EasyP выполняет резолюцию **помодульно (per-module)**. Если в монорепозитории есть два разных сервиса в `proto/user` и `proto/order`:

- `proto/user` может резолвить `common v1.3.0`.
- `proto/order` может независимо использовать `common v2.0.0`.

Каждый proto-модуль имеет собственный `protobuf.mod` и `protobuf.lock`, поэтому команды могут обновлять зависимости независимых сервисов в своём темпе.

## 3. Директивы DSL `protobuf.mod`

Файл `protobuf.mod` располагается в корне proto-модуля и является tool-neutral спецификацией, сфокусированной только на объявлении зависимостей.

```protobuf
// proto/user/protobuf.mod

module github.com/acme/user

roots (
    proto
)

require (
    github.com/googleapis/googleapis v1.5.0
    github.com/acme/weather v1.2.3
    github.com/grpc-ecosystem/grpc-gateway v2.19.0 // indirect
)

// Локальная отладка зависимости
replace github.com/acme/weather => ../weather-fork
```

### Справочник директив

- **`module`**: Объявляет канонический идентификатор (URL/путь) модуля.
- **`roots`**: Задаёт корневую поддиректорию с `.proto` файлами внутри репозитория (по умолчанию `.`). Это позволяет корректно резолвить импорты без срезания путей вручную.
- **`require`**: Прямые и транзитивные зависимости с явными фиксациями SemVer версий.
  - **`// indirect`**: Автоматически дописывается командой `easyp mod tidy` для транзитивных зависимостей, не импортируемых напрямую `.proto` файлами модуля.
- **`replace`**: Переопределяет источник зависимости локальным путем (`../weather-fork`) или другим URL/версией. Используется для локальной отладки.

<Callout type="warn">
Директива `replace` предназначена исключительно для локальной разработки. CI-пайплайны EasyP отклоняют коммиты с активными `replace`.
</Callout>

## 4. Механизм герметичной фиксации `protobuf.lock`

Файл `protobuf.lock` генерируется и обновляется командами `easyp mod tidy` и `easyp mod update`.

```yaml
# protobuf.lock - СГЕНЕРИРОВАННЫЙ ФАЙЛ, НЕ РЕДАКТИРОВАТЬ РУКАМИ
version: 1
modules:
  - source: github.com/googleapis/googleapis
    version: v1.5.0
    commit: 8f3a1c94b2e10a84e
    hash: h1:a9F8zK...
  - source: github.com/acme/weather
    version: v1.2.3
    commit: 51d2e071c89f33b11
    hash: h1:x7B3mL...
  - source: github.com/grpc-ecosystem/grpc-gateway
    version: v2.19.0
    commit: c4f88aa91024e12c4
    hash: h1:p0Q1wK...
```

### Гарантии герметичности сборки

1. **Строгая фиксация**: Сборка в CI выполняется через `easyp mod download` строго по `protobuf.lock`. Состояние кэшей и удалённых реестров не влияет на результат.
2. **Контроль целостности**: Поле `hash` проверяет совпадение содержимого, защищая от подмены Git-тегов или кэша.
3. **Предсказуемый жизненный цикл**: `protobuf.lock` изменяется только при явном вызове `easyp mod tidy` или `easyp mod update`.

## 5. Сравнительный анализ архитектур

| Модель | EasyP MVS | Go Modules (MVS) | Cargo / Rust (PubGrub SAT) | Buf v2 (Workspace SVS) |
| --- | --- | --- | --- | --- |
| **Алгоритм** | Minimal Version Selection | Minimal Version Selection | SAT Solver (PubGrub) | Workspace Single Version |
| **Правило выбора** | `max(минимумов)` | `max(минимумов)` | Сложные SemVer диапазоны (`^1.2.3`) | Единая версия на весь workspace |
| **Скоуп резолюции** | Per-module | Per-module | Per-crate | Весь Workspace |
| **Несколько версий в сборке** | Запрещено (коллизия FQN) | Разрешено для разных major версий | Разрешено для разных major версий | Запрещено |
| **Lock-файл** | `protobuf.lock` | `go.sum` | `Cargo.lock` | `buf.lock` |
| **Локальный оверрайд** | Директива `replace` | Директива `replace` | `[patch]` / `path` | Локальный workspace модуль |

### Почему MVS идеально подходит для Protobuf

Схемы Protobuf требуют строгой уникальности имён пакетов и полных имён сообщений (Fully Qualified Name, FQN) в рамках единицы компиляции. В отличие от Rust (где Cargo может переименовать crate) или Go (где `v2` имеет другой путь импорта), компиляция двух разных версий одного proto-файла в единый descriptor set приводит к немедленным ошибкам коллизии FQN.

MVS в EasyP предоставляет идеальный баланс для Protobuf: детерминированный выбор единой версии внутри графа каждого модуля и полную независимость версий между отдельными сервисами.
