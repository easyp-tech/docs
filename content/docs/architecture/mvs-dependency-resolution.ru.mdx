EasyP разрешает зависимости отдельно для каждого protobuf-модуля. Для требований SemVer применяется **Minimal Version Selection (MVS)**: выбирается максимальная из запрошенных минимальных версий. Точные Git-коммиты и требования без версии имеют отдельные правила; SHA не получает искусственный порядок SemVer.

## Правила выбора

| Требования к одному модулю | Результат |
| --- | --- |
| Несколько SemVer-минимумов | Максимум запрошенных минимумов |
| Один явный полный SHA | Точный коммит |
| Выбранный SemVer и SHA того же коммита | Совместимы; тег сохраняется в lock для SemVer-ограничения |
| Разные явные SHA или выбранный тег на другом коммите | Ошибка конфликта |
| Без версии вместе с SemVer или SHA | Требование без версии не добавляет ограничения |
| Только требования без версии | Tidy использует прежний lock или HEAD без lock; update освежает HEAD |

Коммит нельзя считать «новее» минимальной версии по дате или истории Git. Совместимость SemVer/SHA проверяется по точному коммиту выбранного тега. Если более сильное ограничение заменяет предварительный HEAD, его рёбра зависимостей пересобираются; ошибки и зависимости отброшенного HEAD не остаются в выбранном графе. Циклические неустойчивые ограничения без версии отклоняются.

## Ромбовидная зависимость

~~~text
user
├── common v1.2.0
└── weather v2.1.0
    └── common v1.3.0
~~~

Граф <code>user</code> выбирает <code>common v1.3.0</code> и <code>weather v2.1.0</code>. Численно <code>v1.3.0</code> удовлетворяет обоим минимумам common; разрешение версий само по себе не доказывает совместимость схем. Для этого отдельно запускают <code>easyp breaking</code>.

Если user закрепляет SHA, выбранный тег <code>common v1.3.0</code> должен указывать именно на него. Самого наличия тега <code>v1.2.0</code> на этом SHA недостаточно, если максимум требований — <code>v1.3.0</code>. Если требование user к common не содержит версии, минимум weather определяет выбор.

## Границы модулей и дескрипторов

Каждый модуль имеет свой <code>protobuf.mod</code> и <code>protobuf.lock</code>. Например, <code>proto/user</code> может выбрать <code>common v1.3.0</code>, а <code>proto/order</code> — <code>common v2.0.0</code> в независимых графах.

При генерации независимость графов не гарантирует совместимость объединённого результата:

| Вывод | Проверка |
| --- | --- |
| <code>--descriptor_set_out</code> | Объединяет совместимые графы; конфликт определения по import path или символов — ошибка |
| <code>--descriptor_set_out_dir</code> | Отдельный набор для каждой пары проект/модуль; графы не объединяются |
| Результаты плагинов | Одинаковые общие файлы объединяются; разное содержимое по одному пути или разные Go-пакеты в одном каталоге — ошибка |

Managed-опции сохраняются при проверке совместимости. Разные версии зависимостей могут иметь совместимые дескрипторы, а разные настройки потребителей — сделать их несовместимыми. <code>--include_imports</code> меняет только содержимое экспорта; полный граф проверяется в любом случае. Генерация импортов плагином отдельно управляется <code>with_imports</code>, по умолчанию false.

## Манифест и локальные замены

~~~text
module github.com/acme/user
roots proto
require (
    github.com/acme/common v1.2.0
    github.com/acme/weather v2.1.0
)
replace github.com/acme/weather => ../weather-fork
~~~

<code>roots</code> считается от каталога манифеста и по умолчанию равен <code>.</code>. Команды <code>get</code> и <code>mod</code> находят ближайший манифест в предках в пределах workspace. Транзитивные требования записываются с <code>// indirect</code>.

Относительная цель <code>replace</code> считается от содержащего её <code>protobuf.mod</code>, абсолютная используется напрямую. Генерация и линтинг поддерживают локальные замены. <code>get</code>, <code>mod tidy</code>, <code>mod update</code> и <code>mod vendor</code> отклоняют их: уберите замены перед созданием или использованием воспроизводимого Git lock этими командами. Это проверка команд, а не запрет коммитов со стороны CI.

Для вложенных Git-модулей каждое требование использует имя из соответствующего манифеста. Требование без версии не нуждается в теге. Версия <code>v1.2.3</code> модуля в <code>proto/user</code> использует тег <code>proto/user/v1.2.3</code>.

## Lock и неизменность опубликованных версий

<code>protobuf.lock</code> записывает источник, выбранный тег или SHA, точный коммит и хеш содержимого. Его создают <code>get</code>, <code>mod tidy</code> и <code>mod update</code>. <code>mod download</code> использует точные коммиты из lock. Пример ниже показывает формат, а не реальные данные репозитория.

~~~yaml
version: 1
modules:
  - source: github.com/acme/common
    version: v1.3.0
    commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    hash: h1:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
~~~

При <code>tidy</code>, <code>get</code> и <code>update</code> повторно полученный ранее зафиксированный SemVer должен совпасть с записанными коммитом и хешем. Несовпадение вызывает <code>ErrLockedVersionChanged</code> до установки нового графа и записи манифеста или lock, в том числе для транзитивных требований и прогретого кеша. Новая версия может быть выбрана; неограниченные требования без версии по-прежнему обновляются до HEAD, явные SHA сохраняются.

<code>mod download</code> может получить старый коммит после переноса тега, если коммит остаётся доступным. Хеш Go <code>dirhash.Hash1</code> охватывает обычные файлы, отслеживаемые Git, с путями относительно репозитория. Проверка выполняется и для новых загрузок, и для установленных файлов кеша.

## Повторное использование Git-объектов

Для каждого remote используется общее хранилище объектов. Известный точный коммит повторно используется без обращения к remote. Первая попытка — загрузка нужного коммита с глубиной один. Если сервер запрещает исторический SHA, EasyP получает доступную историю объявленных ссылок и всё равно требует исходный коммит; HEAD вместо него не подставляется. Поэтому холодная загрузка не всегда остаётся shallow. Проверки тегов обновляются отдельно, чтобы кеш не скрывал перепубликацию.

Воспроизводимость зависит от доступности зафиксированных коммитов и совпадения хешей. При breaking-проверке каждая ревизия использует собственные манифесты и lock; база берётся из изолированного Git-снимка, а не из текущего рабочего дерева.
