---
title: "MVS Dependency Resolution"
description: "SemVer selection, compatible commit constraints, and reproducible Git dependencies in EasyP."
---

EasyP resolves dependencies separately for each protobuf module. Semantic requirements use **Minimal Version Selection (MVS)**: select the maximum of the requested minimum versions. Exact Git commits and versionless requirements follow separate rules; SHA values have no invented SemVer ordering.

## Selection rules

| Requirements for one module | Result |
| --- | --- |
| Several SemVer minimums | Maximum requested minimum |
| One explicit full SHA | Exact commit |
| Selected SemVer and SHA of the same commit | Compatible; the tag stays in the lock for the semantic constraint |
| Different explicit SHAs, or selected tag at another commit | Conflict error |
| Versionless alongside SemVer or SHA | Versionless requirement adds no constraint |
| Only versionless requirements | Tidy uses the existing lock pin, or HEAD without one; update refreshes HEAD |

A commit is not considered “newer” than a minimum version based on its date or ancestry. SemVer/SHA compatibility checks the selected tag's exact commit. If a stronger constraint replaces provisional HEAD, its dependency edges are rebuilt; dependencies and errors from discarded HEAD do not remain in the selected graph. Cyclic unstable versionless constraints are rejected.

## Diamond dependency example

~~~text
user
├── common v1.2.0
└── weather v2.1.0
    └── common v1.3.0
~~~

The <code>user</code> graph selects <code>common v1.3.0</code> and <code>weather v2.1.0</code>. Numerically, <code>v1.3.0</code> satisfies both common minimums; dependency resolution does not prove schema compatibility. Run <code>easyp breaking</code> separately for that check.

If user pins a SHA, the selected <code>common v1.3.0</code> tag must point to that exact commit. A <code>v1.2.0</code> tag at that SHA is insufficient when the maximum requirement is <code>v1.3.0</code>. If user's common requirement has no version, weather's semantic minimum determines the selection.

## Module and descriptor boundaries

Each module has its own <code>protobuf.mod</code> and <code>protobuf.lock</code>. For example, <code>proto/user</code> can select <code>common v1.3.0</code> while <code>proto/order</code> selects <code>common v2.0.0</code> in an independent graph.

Independent graphs do not guarantee that their combined generation output is compatible:

| Output | Validation |
| --- | --- |
| <code>--descriptor_set_out</code> | Merges compatible graphs; conflicting definitions by import path or symbol are errors |
| <code>--descriptor_set_out_dir</code> | Independent set per project/module pair; graphs are not merged |
| Plugin output | Identical shared files are deduplicated; different contents at one path or Go packages sharing a directory are errors |

Managed options remain part of compatibility checks. Different dependency versions can have compatible descriptors, while different consumer settings can make them incompatible. <code>--include_imports</code> affects exported contents only; the full graph is always validated. Plugin import generation is separately controlled by <code>with_imports</code>, default false.

## Manifest and local replacements

~~~text
module github.com/acme/user
roots proto
require (
    github.com/acme/common v1.2.0
    github.com/acme/weather v2.1.0
)
replace github.com/acme/weather => ../weather-fork
~~~

<code>roots</code> is relative to the manifest directory and defaults to <code>.</code>. The <code>get</code> and <code>mod</code> commands find the nearest ancestor manifest within the workspace. Transitive requirements are recorded with <code>// indirect</code>.

A relative <code>replace</code> target is resolved from its owning <code>protobuf.mod</code>; an absolute target is used directly. Generation and linting support local replacements. <code>get</code>, <code>mod tidy</code>, <code>mod update</code>, and <code>mod vendor</code> reject them: remove replacements before these commands create or use a reproducible Git lock. This is command validation, not a CI rule rejecting commits.

For nested Git modules, require each identity declared by its manifest. Versionless requirements need no tags. Version <code>v1.2.3</code> of a module in <code>proto/user</code> uses tag <code>proto/user/v1.2.3</code>.

## Locks and immutable published versions

<code>protobuf.lock</code> records the source, selected tag or SHA, exact commit, and content hash. It is created by <code>get</code>, <code>mod tidy</code>, and <code>mod update</code>. <code>mod download</code> uses exact locked commits. The example below illustrates the format, not actual repository data.

~~~yaml
version: 1
modules:
  - source: github.com/acme/common
    version: v1.3.0
    commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    hash: h1:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
~~~

During <code>tidy</code>, <code>get</code>, and <code>update</code>, a fetched previously locked SemVer must match its recorded commit and hash. A mismatch raises <code>ErrLockedVersionChanged</code> before installing the new graph or writing the manifest or lock, including for transitive requirements and warm caches. A new version may be selected; unconstrained versionless requirements still refresh to HEAD, while explicit SHAs stay pinned.

<code>mod download</code> can retrieve the old commit after a tag moves if that commit remains available. The Go <code>dirhash.Hash1</code> digest covers Git-tracked regular files with repository-relative paths. Both newly downloaded and installed cached files are verified.

## Git object reuse

A shared object store is used per remote. Known exact commits can be reused without remote access. The first attempt fetches the requested commit at depth one. If a server rejects a historical SHA, EasyP fetches advertised reachable history and still requires the original commit; HEAD is never substituted. A cold fetch is therefore not always shallow. Tag lookups are refreshed separately so cache reuse cannot hide republishing.

Reproducibility depends on pinned commits remaining available and hashes matching. Breaking checks use each revision's own manifests and locks; the baseline is read from an isolated Git snapshot rather than the current working tree.

See [protobuf.mod](/docs/reference/protobuf-mod), [protobuf.lock](/docs/reference/protobuf-lock), and [generation](/docs/cli/generator) for details.
