EasyP — современный инструментарий для Protocol Buffers, объединяющий весь рабочий процесс в один CLI (`easyp`) и дополнительный MCP-сервер (`easyp-mcp`). Он совмещает встроенный pure-Go компилятор, линтинг, Git-нативный менеджер пакетов, генерацию кода и проверку совместимости API.

## Проблема: фрагментированные protobuf-процессы

Работа с Protocol Buffers в командах часто создаёт лишнюю сложность:

### Хаос инструментов
- **Много отдельных утилит**: Разные бинарники для `protoc`, линтинга, проверки совместимости, генерации и синхронизации схем
- **Несогласованные конфигурации**: Самописные shell-скрипты и разные флаги в каждом сервисе
- **Сложный онбординг**: Разработчикам приходится вручную ставить совпадающие версии `protoc` и плагинов до первой сборки

### Проблемы управления зависимостями
- **Нет единого стандарта**: Проекты копируют `.proto`-файлы вручную или опираются на хрупкие Git submodules
- **Конфликты версий**: Трудно согласовать транзитивные зависимости между командами
- **Неповторяемость сборок**: Локальное окружение и CI собирают разные дескрипторы и код

### Риски совместимости и привязка к вендору
- **Ручное ревью**: Ломающие изменения API проходят без автоматической проверки относительно Git-базы
- **Привязка к внешнему реестру**: Командам приходится переносить контракты во внешний реестр, хотя код уже живёт в Git

## Решение: EasyP v1

EasyP заменяет разрозненные скрипты вокруг `protoc` цельной архитектурой v1 на четырёх опорах:

### Встроенный pure-Go компилятор (`easyprotoc`)
EasyP v1 компилирует `.proto`-файлы собственным pure-Go компилятором **`easyprotoc`** (`v0.1.1`) — **установка `protoc` не требуется**, а сторонние обёртки (`protocompile`, `go-protoparser`) больше не нужны:
- Формирует `FileDescriptorSet`, эквивалентный выводу `protoc` (проверяется на всём корпусе `googleapis` в CI), включая source info, комментарии и пользовательские опции
- Поставляется со встроенными стандартными типами `google/protobuf/*.proto`
- Поддерживает **proto2**, **proto3** и **Protobuf Editions 2023**
- Компилирует файлы параллельно на всех ядрах CPU (например, компиляция всех 7 416 файлов `googleapis` с `--include_imports --include_source_info` занимает ~0,88 с против ~3,83 с у `protoc` на Apple M5 Pro)

### Чёткое разделение конфигурационных файлов
Вместо одного перегруженного файла EasyP v1 разделяет ответственность между тремя понятными файлами и lock-файлом:
- **`protobuf.mod`** (+ **`protobuf.lock`**) — идентификатор модуля, корни исходников `roots`, Git-зависимости `require` с разрешением версий по MVS и локальные подмены `replace`
- **`easyp.yaml`** — политики линтинга (`44` встроенных правила) и проверки совместимости (`69` правил в профилях `FILE`, `PACKAGE`, `WIRE_JSON`, `WIRE`)
- **`easyp.gen.yaml`** — цели генерации (`modules`, `paths`, `packages`), managed mode и список `plugins`

### Git-нативные зависимости
Любой Git-репозиторий (GitHub, GitLab, Bitbucket или корпоративный self-hosted Git) работает как модуль protobuf напрямую. EasyP проверяет полные SHA коммитов и селективные хеши `dirhash.Hash1` в `protobuf.lock`, а флаг `--frozen` в CI гарантирует воспроизводимость без изменений файлов.

### Поддержка ИИ-агентов через `easyp-mcp`
Архивы релизов, формула Homebrew и сборка через Go также включают `easyp-mcp` — stdio-сервер Model Context Protocol с инструментом `easyp_config_describe`, работающим на тех же JSON Schema, что и `easyp validate-config`.

## Ключевые возможности

| Возможность | Описание |
|-------------|----------|
| **Встроенный компилятор `easyprotoc`** | Pure-Go компилятор `.proto` без `protoc`, со встроенными well-known типами и поддержкой Protobuf Editions 2023. |
| **Линтинг API** | 44 правила в группах `MINIMAL`, `BASIC`, `DEFAULT`, `COMMENTS` и `UNARY_RPC` с переиспользуемыми политиками через `extends`. |
| **Проверка breaking changes** | 69 правил на базе дескрипторов в профилях `FILE`, `PACKAGE`, `WIRE_JSON` и `WIRE` относительно любой ветки, тега или коммита Git. |
| **Git-нативный менеджер пакетов** | Разрешение версий по MVS, `easyp get`, `mod tidy`/`download`/`update`/`vendor`, локальный `replace` и криптографическая проверка `protobuf.lock`. |
| **Гибкая генерация кода** | 15 встроенных WASM-плагинов, локальные плагины (`name`, `path`, `command`) и удалённые плагины через EasyP API Service. |
| **Удобство разработки и агентов** | `easyp validate-config`, вывод `--format json`, автодополнение bash/zsh и stdio-сервер `easyp-mcp`. |

## Поддерживаемые источники плагинов

В `easyp.gen.yaml` каждый элемент `plugins:` задаёт ровно один из четырёх источников запуска:

### Локальные и встроенные WASM-плагины (`name:`)
Запускает `protoc-gen-<name>` из `PATH` или использует один из **15 встроенных WASM-плагинов** (`cpp`, `csharp`, `java`, `kotlin`, `objc`, `php`, `python`, `ruby` и их gRPC-пары `grpc_*`):
```yaml
version: v1
plugins:
  - name: python
    out: ./gen/python
```

### Явный путь к бинарнику (`path:`)
Запускает указанный исполняемый файл (относительные пути разрешаются от рабочего каталога запуска `easyp generate`):
```yaml
version: v1
plugins:
  - path: ./tools/bin/protoc-gen-custom
    out: ./gen/custom
```

### Команда с аргументами (`command:`)
Запускает обёртку, интерпретатор или команду запуска вроде `go run` или `npx`:
```yaml
version: v1
plugins:
  - command: ["go", "run", "./cmd/protoc-gen-internal"]
    out: ./gen/internal
```

### Удалённые плагины (`remote:` + `version:`)
Выполняет зафиксированные версии плагинов через [`plugins.easyp.tech`](/ru/plugins) или собственный [EasyP API Service](/ru/docs/api-service/overview) без локальной установки плагинов:
```yaml
version: v1
plugins:
  - remote: plugins.easyp.tech/protocolbuffers/go
    version: v1.36.11
    out: ./gen/go
    opts:
      paths: source_relative
```

## Децентрализованное управление пакетами

В отличие от инструментов, привязанных к централизованному реестру, любой Git-репозиторий может служить источником модулей:

- **Гибкость и контроль**: Работает с GitHub, GitLab, Bitbucket и закрытыми корпоративными Git-серверами
- **Нет привязки к вендору**: Контракты остаются в ваших репозиториях под существующими правами доступа и процессом ревью
- **Воспроизводимость по умолчанию**: `protobuf.lock` фиксирует полные SHA коммитов и хеши содержимого, которые проверяются флагом `--frozen` в CI

## Зависимости с конфигурацией Buf

Проект EasyP v1 объявляет Git-зависимости в `protobuf.mod`. Если Git-зависимость использует конфигурацию Buf v1, v1beta1 или v2 (`buf.yaml` / `buf.work.yaml`), EasyP автоматически читает её корни исходников, фильтры `includes`/`excludes` и поддерживаемые сопоставления BSR. Старые репозитории с конфигом EasyP v0 поддерживаются аналогично, а сам проект-потребитель использует нативные файлы `protobuf.mod`, `easyp.gen.yaml` и `easyp.yaml`.

Поддерживаемые форматы и ограничения описаны на странице [Git-зависимостей с конфигом Buf](/ru/docs/cli/package-manager/easyp-vs-buf).

## Почему выбирают EasyP?

### Для разработчиков
- **Без установки `protoc`**: Один бинарник для компиляции, линтинга, проверки совместимости и генерации за минуты
- **Единый процесс**: Согласованный CLI для всех задач с Protobuf
- **Точная диагностика**: Файл, строка и столбец для ошибок синтаксиса, линтинга, совместимости и конфигурации

### Для команд
- **Единые стандарты**: Переиспользуйте корпоративные политики линтинга и breaking-проверок через Git-модули (`extends`)
- **Воспроизводимые сборки**: `protobuf.lock` и `--frozen` синхронизируют локальные машины и CI
- **Мультиязычная генерация**: Комбинируйте встроенные WASM-, локальные (`path`/`command`) и удалённые плагины в одном `easyp.gen.yaml`

### Для организаций
- **Нет vendor lock-in**: Git-нативные модули работают с приватными репозиториями и закрытыми контурами
- **Собственный сервис плагинов**: Разверните [EasyP API Service](/ru/docs/api-service/overview) для внутренних плагинов
- **Готовность к CI/CD**: Простая интеграция с [GitHub Actions](/ru/docs/ci-cd/github-actions) и [GitLab CI](/ru/docs/ci-cd/gitlab)
