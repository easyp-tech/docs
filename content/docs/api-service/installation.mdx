## Deployment prerequisites

Every deployment needs PostgreSQL and a directory accessible to the service account for trusted plugin executables. S3-compatible storage is optional. A fresh database is migrated at startup; the database role needs the corresponding DDL permissions. Installing the server does not install or register the plugin catalog. See [Plugins](./plugins).

This page follows service/SDK release **v1.0.2**, Helm chart **1.0.2** (appVersion **v1.0.2**), and Go **1.26.6** from the checked manifests. The checked runtime source matches that release; later source changes concern documentation and the development Compose healthcheck.

## Docker image and release channels

The release workflow names the image <code>ghcr.io/easyp-tech/service</code>. Its channels have different meanings:

| Tag | Meaning | Selection advice |
| --- | --- | --- |
| <code>v1.0.2</code> / <code>vX.Y.Z</code> | Versioned release. | Match configuration and release notes; retain the resolved digest. |
| <code>latest</code> | Most recent published release, not current master. | Mutable; avoid it as a reproducibility guarantee. |
| <code>edge</code> | Successful build from master. | Moving development channel; not a release promise. |
| <code>sha-&lt;seven-character-commit&gt;</code> | Commit-addressed edge build. | More specific than edge, but the immutable content identity is still the digest. |

Workflows build Linux amd64 and arm64 images. Version/commit tags are naming conventions, not proof that a registry prevents replacement. Published image/chart availability was not exercised by this documentation audit.

The image entrypoint is <code>/easyp-svc</code> and **has no default command**: pass <code>service start</code>. The runtime is Debian Bookworm slim with CA certificates and UID/GID 65532; it does not bundle every language runtime needed by arbitrary plugins. Mount the configured file and set <code>EASYP&#95;CONFIG</code> so the separate image healthcheck sees it too:

~~~sh
docker run --rm --name easyp-service \
  -e EASYP_CONFIG=/run/easyp/service.yaml \
  -p 127.0.0.1:23410:23410 \
  -p 127.0.0.1:23412:23412 \
  --mount type=bind,src="$PWD/service.yaml",dst=/run/easyp/service.yaml,readonly \
  --mount type=bind,src="$PWD/plugins",dst=/plugins \
  ghcr.io/easyp-tech/service:v1.0.2 service start
~~~
Prepare <code>service.yaml</code> with a database reachable **from the container**. <code>localhost</code> inside the container is not the host’s PostgreSQL. The plugin mount must be readable/executable by UID 65532 and writable when S3 cache extraction is used. Bind published development ports to loopback; configure TLS and access controls before exposing them. The image healthcheck probes liveness <code>/live</code>, not database readiness.

For a source build that does not use GHCR:

~~~sh
git clone --branch v1.0.2 https://github.com/easyp-tech/service.git
cd service
docker build --build-arg VERSION=v1.0.2 -t easyp-service:local .
~~~
Dockerfile build steps can fetch dependencies and base images. This is not an air-gapped build recipe; pre-stage and verify those artifacts for disconnected environments.

## Compose

The repository contains a development Compose stack and a larger deployment/observability stack. The latter includes site-specific routing, credentials, tier assumptions, and telemetry services; it is not a universal one-command production installation. Use the isolated [Quickstart](./quickstart) for one PostgreSQL instance, one service, and one plugin. Do not copy production hostnames or credentials from historical examples.

Always inspect <code>docker compose config</code> before starting a stack. Keep the server config path consistent with its healthcheck via <code>EASYP&#95;CONFIG</code> or an explicit healthcheck <code>--cfg</code>. Database readiness and an actual generation are separate checks.

## Standalone binaries

The GoReleaser configuration builds <code>easyp-svc</code> for Linux and macOS, amd64 and arm64, with CGO disabled. Release archives use the name <code>easyp-svc&#95;1.0.2&#95;&lt;os&gt;&#95;&lt;arch&gt;.tar.gz</code> and include LICENSE and README; the release workflow also produces checksums and software-bill-of-materials artifacts. Obtain the appropriate archive from the [service release](https://github.com/easyp-tech/service/releases/tag/v1.0.2), verify its checksum, and retain the exact artifact. This audit compiled local binaries but did not verify downloaded release assets.

~~~sh
go build -trimpath -ldflags='-X main.version=v1.0.2' \
  -o ./easyp-svc ./cmd/easyp-svc
./easyp-svc config validate --cfg ./service.yaml
./easyp-svc service start --cfg ./service.yaml
~~~
The Go version in go.mod is the source-build requirement. A Linux executable extracted from a plugin build is not runnable by a macOS server merely because the operator binary is available on macOS. Match each plugin artifact and its sidecars to the server OS, architecture, and installed runtime.

## Helm installation

The chart reference is <code>oci://ghcr.io/easyp-tech/charts/easyp-service</code>. It deploys the service, not PostgreSQL or your object store. Before installation, provide an existing Kubernetes Secret with <code>DB&#95;POSTGRES&#95;DSN</code> and any required <code>AUTH&#95;WRITE&#95;TOKENS</code>, license, or S3 credential environment values; alternatively set <code>secrets.create</code> and <code>secrets.data</code> through a protected values source. Do not commit credentials into a values file.

With TLS enabled, provide <code>tls.serverSecret</code> or enable cert-manager with a configured issuer. The default empty <code>tls.clientCASecret</code> means the server Secret must also contain <code>ca.crt</code> and the service requires client certificates. Set it to <code>"-"</code> only when server-authenticated TLS without mTLS is the deliberate policy. Application bearer authentication remains independent.

~~~yaml
secrets:
  existingSecret: easyp-service-env
tls:
  enabled: true
  serverSecret: easyp-service-tls
  clientCASecret: "-"
extraEnv:
  - name: AUTH_REQUIRE_AUTHENTICATION
    value: "true"
~~~
This example requires a bearer-capable client such as the Go SDK; the current <code>easyp</code> remote executor cannot supply the token. It also needs an artifact provisioning strategy: S3 configured in the values below or a populated local plugin volume.

~~~sh
helm template easyp ./deploy/charts/easyp-service --values values.yaml
helm upgrade --install easyp oci://ghcr.io/easyp-tech/charts/easyp-service \
  --version 1.0.2 --namespace easyp --create-namespace --values values.yaml
~~~
The first command renders a local checkout; the second installs into the user’s cluster and accesses the registry. They are instructions, not actions performed by this audit.

## Required and hazardous chart choices

The default one-replica deployment uses Recreate and a ReadWriteOnce volume. Multiple replicas with RWO are rejected by the chart. Although RWX passes that check, the plugin cache has no cross-process coordination: do not turn that validation escape into a shared-cache high-availability recommendation. Plan separate private caches and test the complete topology.

Storage must be strictly larger than the positive cache budget. With persistence disabled, the ephemeral-storage limit must also exceed the emptyDir limit; simply switching persistence off with the shipped 2 GiB resource limit and 25 GiB emptyDir does not render successfully. The memory guard checks <code>2 × maxConcurrentGenerations × maxOutputSize</code>; this is not a cap on child memory or a complete capacity model. Shutdown must satisfy <code>terminationGracePeriodSeconds &gt; forceShutdownAfterSeconds &gt; generationTimeoutSeconds</code>.

Ingress requires a hostname and trusted-proxy CIDRs. Current chart validation additionally demands a client certificate for its enabled ServersTransport even when <code>clientCASecret: "-"</code> selects server-only TLS: treat this as a chart limitation, not a service mTLS requirement. Traefik-specific resources require the appropriate CRDs/controller configuration.

NetworkPolicy is enabled by default. An empty ingress namespace selector does not restrict gRPC callers to a chosen namespace. Allowed egress ports are not destination allowlists. **The template does not add an ingress rule for MCP when MCP is enabled**; supply an explicitly reviewed additional policy for authorized MCP access. Its default egress also does not include every possible S3 or profiling port.

ServiceMonitor/PrometheusRule require monitoring CRDs. The reloader annotation works only if a compatible reloader controller is installed; it is not built-in secret hot-reload. Review permissions and exposure of metrics and health as operational data.
