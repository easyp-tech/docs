## Путь запроса

<code>easyp.generator.v1.GeneratorAPI/GenerateCode</code> принимает координаты плагина и стандартный запрос плагина Protobuf. Прикладная gRPC-цепочка, от внешнего интерсептора к внутреннему:

~~~text
trace_logging
  -> realip
  -> перенос IP вызывающего в context
  -> Prometheus
  -> structured_logging
  -> panic_recovery
  -> validation middleware
  -> rate_limit
  -> concurrency_limit
  -> auth
  -> license
  -> error_code_conversion
  -> GenerateCode handler -> Core -> WorkerPool -> registry -> дочерний процесс
~~~
TLS — настройка транспорта, а не интерсептор. OpenTelemetry использует gRPC stats handler и обёртки Core/registry/plugin. Преобразование ошибок находится **внутри** интерсепторов аутентификации и лимитирования, непосредственно перед обработчиком. Поэтому <code>ErrorInfo</code> добавляется не ко всем отклонённым RPC.

Зарегистрированный validation middleware ищет сгенерированные методы валидации. В проверенных сообщениях API нет реализаций <code>Validate</code>/<code>ValidateAll</code>; наличие ограничений в <code>generator.proto</code> не доказывает, что этот middleware их применяет. Фактические проверки находятся в обработчиках и Core.

Core разбирает <code>group/name:version</code>, получает плагин через lookup pool, занимает слот генерации, сериализует запрос, запускает процесс и десериализует stdout как <code>CodeGeneratorResponse</code>. Поле <code>error</code> в этом ответе — результат протокола плагина, который не становится автоматически gRPC-ошибкой. Клиент должен проверять оба уровня.

## Идентификатор и выбор версии

Регистрация содержит group, name и version, конфигурацию и tags. Задавайте явную версию, например <code>protocolbuffers/go:v1.36.11</code>. В wire-запросе компонент версии обязателен. Парсер URL в <code>easyp</code> подставляет <code>latest</code>, когда версия отсутствует в URL.

Для <code>latest</code> выполняется PostgreSQL-запрос <code>ORDER BY version DESC LIMIT 1</code>: это **текстовая сортировка**, не сравнение SemVer и не время регистрации. Например, строка <code>v1.36.9</code> может оказаться выше <code>v1.36.11</code>. Не используйте <code>latest</code> для воспроизводимых сборок. Сервис не обеспечивает неизменяемость артефакта под существующей версией.

Каталог фильтруется по точному совпадению group/name/version и наличию всех запрошенных tags. Размер страницы по умолчанию — 100, максимум — 1000. Пагинация keyset-based, с порядком group/name/version; между страницами сохраняйте фильтры. Курсор кодирует координаты, а не подписанный снимок всего каталога.

## Поиск и генерация — разные очереди

<code>worker&#95;pool.workers</code> определяет число workers для **поиска и загрузки плагинов**, а не число работающих дочерних процессов. <code>Get()</code> пытается поставить lookup в очередь без блокирующего ожидания свободного места; заполненная очередь возвращает <code>ErrServerOverloaded</code>. Принятый запрос затем ожидает результат или отмену. Отдельно существуют семафор генерации и ограниченная очередь ожидающих слот генерации.

| Настройка | Дефолт бинарника | Значение |
| --- | --- | --- |
| <code>worker&#95;pool.workers</code> | 4 | Параллельные lookup workers; потолок Community — 4. |
| <code>worker&#95;pool.queue&#95;size</code> | 16 | Ёмкость очереди lookup и, отдельно, очереди ожидания генерации. |
| <code>worker&#95;pool.max&#95;concurrent&#95;generations</code> | 16 | Активные генерации; потолок Community — 16. |
| <code>rate&#95;limit.max&#95;concurrent&#95;per&#95;ip</code> | 2 | Более раннее ограничение по определённому IP клиента; 0 отключает именно этот лимит. |
| <code>worker&#95;pool.generation&#95;timeout</code> | 120s | Бюджет исполнения после допуска к генерации, не всего пути с lookup и ожиданием. |
| <code>worker&#95;pool.max&#95;retries</code> | 2 | До двух дополнительных попыток для распознанных пулом временных ошибок генерации. |

Пул распознаёт временные ошибки по конкретным фрагментам текста, а не по исчерпывающей классификации сбоев плагина. Между собственными попытками исполнения он не добавляет exponential backoff. Более ранний deadline клиента сохраняет силу. Из этих дефолтов нельзя вычислять обещанную производительность: стоимость плагина, хранилища, дескрипторов и ожидания зависит от нагрузки.

## Исполнение процесса

Registry вызывает <code>exec.CommandContext</code> с зарегистрированной командой. В stdin поступает сериализованный запрос, в stdout ожидается сериализованный ответ. Окружение передаётся явно. Рабочий каталог наследуется от сервиса; wrapper, которому нужны соседние файлы, должен определять собственный каталог, а не считать текущим каталог плагина.

По умолчанию stdout ограничен 64 MiB, захват stderr — 1 MiB. Исполнение могут прервать таймаут конфигурации плагина и context пула. На поддерживаемых Unix-платформах отмена адресована группе процессов. Ограничение вывода не ограничивает память дочернего процесса и не создаёт песочницу. Если читатель достиг лимита, а процесс продолжает заполнять pipe, ожидание может продлиться до отмены; лимит не гарантирует немедленное завершение процесса.

Путь executable проверяется относительно каталога плагинов, но разрешённый код сохраняет права учётной записи сервиса на файловую систему и сеть. См. [Модель безопасности](./security).

## Локальное хранилище и S3

Метаданные PostgreSQL нужны в обоих режимах. Без S3 bucket каталог <code>plugins&#95;dir</code> является основным хранилищем артефактов: заполняйте и резервируйте его самостоятельно. Регистрация не загружает и не распространяет эти файлы.

С S3 используется путь <code>prefix/group/name/version/plugin.tgz</code>. Сначала загрузите архив, затем регистрируйте плагин. <code>CreatePlugin</code> и изменение конфигурации читают архив и сохраняют SHA-256. Холодный lookup скачивает архив, проверяет записанный хеш при его наличии, распаковывает во временный каталог, удаляет прежний destination и переименовывает временный каталог. Последовательность remove/rename не является атомарной заменой существующего каталога.

Одновременные холодные загрузки одной версии объединяются через process-local singleflight. Используется context запроса, начавшего операцию; межрепличной блокировки нет. Распаковка отклоняет небезопасные пути и выходящие наружу symlink targets, пропускает неподдерживаемые специальные entries. Отдельного настраиваемого лимита распакованного размера архива нет.

При тёплом попадании проверяется наличие локального executable; хеш архива **не пересчитывается перед каждым запуском**. Старые записи без хеша остаются без проверки при скачивании, пока явное изменение конфигурации не запишет checksum. Обновление метаданных не инвалидирует тёплую локальную копию. Замена S3-объекта под прежней версией может оставить старые байты на тёплых репликах и вызвать checksum mismatch на холодных.

Дефолтный мягкий LRU-бюджет S3-кэша — 20 GiB. Ноль отключает вытеснение. Недавно использованные entries защищены не меньше пяти минут или двух generation timeouts, если это больше; при защищённых entries бюджет может быть превышен. Межпроцессного координатора и счётчика активных исполнений нет. Разделяйте каталоги кэша реплик. Удаление регистрации после операции БД пытается удалить объект S3 и локальный кэш; это не общая транзакция трёх хранилищ.

## PostgreSQL и health

Встроенные миграции Goose выполняются до readiness. PostgreSQL хранит регистрации и партиционированный аудит, но не сгенерированные файлы. Первая миграция создаёт обычную таблицу аудита; вторая копирует её в месячные UTC-партиции и заменяет прежнюю таблицу. Планируйте блокировки и дополнительное место, а не считайте это изменением только метаданных.

HTTP <code>/live</code> отражает liveness процесса независимо от PostgreSQL. HTTP <code>/</code> возвращает not-ready при старте, затем проверяет PostgreSQL. Ни один из endpoint не проверяет все плагины, S3-объекты, лицензию или экспортёры. gRPC health объявляет serving status, но не является database-aware readiness. Для доступности БД используйте HTTP readiness, для всего пути — отдельную синтетическую генерацию.

## Доставка аудита

Core создаёт событие по результату операции. Enterprise разрешает постановку в очередь; Community увеличивает метрики пропущенного аудита. Отказы ранних интерсепторов аутентификации и допуска не являются событиями аудита Core.

Дефолты: очередь на 1000 событий, batch на 100, flush раз в секунду, ожидание enqueue до секунды и бюджет записи batch пять секунд. Ожидание enqueue намеренно переживает отмену запроса и может добавлять задержку. При enqueue timeout теряется событие; после неудачных попыток сохранения теряется batch. Три настроенных retry означают до четырёх попыток записи в пределах бюджета. Долговечной очереди, replay API и гарантии exactly-once нет.

Обслуживание партиций запускается при старте и каждые шесть часов. Создаются текущий месяц и три будущих. Retention 12 удаляет партиции строго старше начала месяца двенадцать месяцев назад: текущий месяц учитывается дополнительно. Ноль отключает удаление по retention. DEFAULT-партиция автоматически не очищается и не удаляется. До использования retention и maintenance gauges прочитайте [Наблюдаемость](./observability) и соответствующие [runbooks](./runbooks).

## Контракт ошибок этой ревизии

| Условие, дошедшее до преобразования ошибок обработчика | gRPC-код / reason |
| --- | --- |
| Регистрация отсутствует | <code>NotFound</code> / <code>NOT&#95;FOUND</code> |
| Заполнена очередь допуска lookup или генерации | <code>ResourceExhausted</code> / <code>SERVER&#95;OVERLOADED</code> |
| Достигнут потолок регистраций Community | <code>ResourceExhausted</code> / <code>MAX&#95;PLUGINS&#95;EXCEEDED</code> |
| Архив отсутствует при регистрации с S3 | <code>FailedPrecondition</code> / <code>BINARY&#95;NOT&#95;UPLOADED</code> |
| Ошибка объектного хранилища при холодном lookup | <code>Unavailable</code> / <code>STORAGE&#95;UNAVAILABLE</code> |
| Дубликат регистрации | <code>AlreadyExists</code> / <code>ALREADY&#95;EXISTS</code> |
| Ошибка исполнения или протокола, обёрнутая как generation failure | <code>Internal</code> / <code>GENERATION&#95;FAILED</code> |

Преобразованные ошибки содержат <code>google.rpc.ErrorInfo</code> с domain <code>easyp.tech</code>. Есть важные дефекты текущей реализации: созданный обработчиком status <code>InvalidArgument</code>, например для неверного page token или update mask, превращается в <code>Internal</code>; таймаут плагина, обёрнутый в <code>ErrGenerationFailed</code>, также становится <code>Internal</code>, потому что эта проверка предшествует проверке deadline. Истёкший deadline самого клиента всё ещё может выглядеть как <code>DeadlineExceeded</code>. Не стройте retry policy на предположении, что все таймауты и ошибки ввода имеют ожидаемые коды.
