## Компоненты

```
                 ┌────────────────────────── easyp-svc (один процесс) ──────────────────────────┐
 :23410 gRPC ───▶│ цепочка интерсепторов ─▶ API-хендлеры ─▶ core ─▶ WorkerPool ─▶ Registry     │
 :23411 HTTP ───▶│ /metrics                                        │            │   │            │
 :23412 HTTP ───▶│ /live  /  (readiness: PostgreSQL)               │            │   └─▶ exec плагина
 :23413 HTTP ───▶│ /mcp  (только при mcp.enabled)                  │            ▼                │
                 │                                  воркер аудита ◀┘        кеш плагинов (диск)  │
                 └───────────────────────────────────────┬──────────────────────┬───────────────┘
                                                          ▼                      ▼
                                                     PostgreSQL          S3-совместимое хранилище
                                                 plugins, audit_log        архивы плагинов
```

Один бинарник `easyp-svc` — это и сервер (`service start`), и CLI оператора.
Отдельного процесса-воркера и контейнерного рантайма нет.

## Путь запроса

Вызов `GenerateCode` проходит через интерсепторы, от внешнего к внутреннему:

| # | Интерсептор | Что делает |
|---|---|---|
| 1 | trace logging | Кладёт trace ID в логгер запроса. |
| 2 | real IP | Берёт адрес клиента из `X-Forwarded-For`/`X-Real-IP`, но только от пиров из `server.trusted_proxies`. |
| 3 | caller IP | Запоминает итоговый адрес для лимитеров и аудита. |
| 4 | Prometheus | Метрики `easyp_api_grpc_server_*`. |
| 5 | logging | Структурированный лог запроса. |
| 6 | panic recovery | Превращает панику в `INTERNAL` и считает её в `easyp_panics_total`. |
| 7 | validation | Вызывает `Validate()` у сообщений, которые его реализуют. Сгенерированные сообщения `easyp.generator.v1` его не реализуют, поэтому в v1.0.2 это проход насквозь; имена, версии и конфиги плагинов проверяются в core. |
| 8 | rate limit | Token bucket на адрес клиента: `rate_limit.requests_per_second`, `rate_limit.burst`. Отказ: `RESOURCE_EXHAUSTED`. |
| 9 | concurrency limit | Не больше `rate_limit.max_concurrent_per_ip` запросов в полёте на адрес. Отказ: `RESOURCE_EXHAUSTED`. |
| 10 | auth | Проверка bearer-токена: всегда для записи, для всего — при `auth.require_authentication`. Отказ: `UNAUTHENTICATED`. |
| 11 | licence | Отклоняет методы, привязанные к фиче, которой нет в лицензии (`PERMISSION_DENIED`). В v1.0.2 ни один метод не привязан, так что он пропускает всё; лицензия применяется в core (аудит, число плагинов) и при старте (потолки воркеров). |
| 12 | error code conversion | Самый внутренний. Переводит доменные ошибки хендлера в gRPC-коды и добавляет `google.rpc.ErrorInfo`. |

Конвертер кодов стоит последним намеренно: интерсепторы уже возвращают
gRPC-статусы, и конвертация снаружи переписала бы их в `INTERNAL`.

Аудит — не интерсептор. Core записывает каждую операцию, успешную или нет, по
факту.

## Поиск плагина

Имя плагина — `group/name:version`. `group` и `name` соответствуют
`^[a-z][a-z0-9-]*$`; `version` — `^v\d+\.\d+(\.\d+)?$` или литерал `latest`.
Сервису часть `:version` нужна обязательно — easyp CLI сам дописывает `:latest`,
если в `remote:` её нет.

<Callout type="warn">
`latest` выбирает зарегистрированную версию, которая **при сравнении строк**
оказывается последней (`ORDER BY version DESC` по текстовой колонке). Если
зарегистрированы `v1.36.9` и `v1.36.10`, `latest` — это `v1.36.9`. Фиксируйте
версии.
</Callout>

## Пул воркеров: два лимита, один размер очереди

Ограничены два разных ресурса, потому что они заканчиваются по разным причинам:

| Лимит | Настройка | Что ограничивает |
|---|---|---|
| Воркеры поиска | `worker_pool.workers` (4) | Поиск плагина: чтение из БД и, при промахе кеша, скачивание и распаковка. Упирается в сеть. |
| Слоты генерации | `worker_pool.max_concurrent_generations` (16) | Запущенные процессы плагинов. Упирается в CPU и память. |

Оба используют `worker_pool.queue_size` (16) как очередь ожидания:

- Поиск: `Get()` не блокируется. Если очередь заданий полна, он сразу
  возвращает `ErrServerOverloaded`.
- Генерация: запрос, не нашедший свободного слота, ждёт — если только уже не
  ждут `queue_size` запросов; тогда он отклоняется.

В обоих случаях клиент получает `RESOURCE_EXHAUSTED` с reason
`SERVER_OVERLOADED`. Бесконечной очереди нет: ожидающие запросы держат
соединения и память.

Время ожидания слота не входит в `worker_pool.generation_timeout` (120 с).
Собственный `timeout` плагина из его конфига действует внутри этого, так что
побеждает меньший.

Повторы на сервере узкие: до `worker_pool.max_retries` (2) дополнительных
попыток и только если текст ошибки содержит `connection refused` или
`temporary failure`. Таймаут не повторяется никогда.

## Исполнение плагина

- Исполняемый файл — `command[0]` из зарегистрированного конфига плагина,
  аргументы — `command[1:]`. После разрешения симлинков он обязан лежать внутри
  `registry.plugins_dir`.
- Окружение пустое, кроме карты `env` из конфига плагина. Учётные данные самого
  сервиса не наследуются.
- Запрос пишется в stdin. Stdout читается до `registry.max_output_size`
  (64 МиБ); больше — генерация завершается ошибкой. Stderr сохраняется до 1 МиБ
  для сообщения об ошибке.
- Процесс получает свою группу процессов, и по таймауту вся группа убивается
  `SIGKILL`.
- Рабочая директория не задаётся — она та же, что у сервиса.

Это вся изоляция. Чего она не покрывает — в
[Безопасности](/ru/docs/api-service/security).

## Хранение плагинов

**Локальный режим** (нет `registry.s3.bucket`): бинарники плагинов уже должны
лежать в `plugins_dir` — собраны там, смонтированы или вшиты в образ. Запись в
реестре только указывает на них.

**Режим объектного хранилища**: `plugins_dir` — это кеш.

1. Оператор упаковывает каталог каждой версии в
   `{group}/{name}/{version}/plugin.tgz` и загружает его (`easyp-svc plugins push`).
2. Регистрация (`CreatePlugin`) читает архив из хранилища и записывает его
   sha256 в конфиг плагина. Если архива нет, регистрация падает с
   `FAILED_PRECONDITION` / `BINARY_NOT_UPLOADED`. Клиент не может подставить хеш.
3. При первом запросе этой версии архив скачивается в `plugins_dir/.tmp`, его
   sha256 сверяется с записанным, и он распаковывается. Одновременные промахи
   по одному ключу делят одно скачивание.
4. Распакованные каталоги вытесняются по LRU, когда их объём превышает
   `registry.cache_max_bytes` (20 ГиБ). Архив в хранилище остаётся.

Поэтому порядок — **build → push → register**. Повторная загрузка архива с
`--force` после регистрации меняет объект под записанной контрольной суммой, и
следующее скачивание падает с `plugin archive checksum mismatch`, пока плагин не
зарегистрируют заново.

Недоступность хранилища или исчезнувший из бакета архив дают при генерации
`UNAVAILABLE` / `STORAGE_UNAVAILABLE`.

## PostgreSQL

| Таблица | Содержимое |
|---|---|
| `plugins` | По строке на версию плагина: `group_name`, `name`, `version` (text), `config` (command, env, timeout, sha256), `tags`. Уникальность по (group, name, version). |
| `audit_log` | Журнал аудита Enterprise, партиции по месяцам плюс `audit_log_default`. |
| `goose_db_version` | Применённые миграции. |

Миграции встроены в бинарник и применяются сервисом при старте под сессионной
блокировкой PostgreSQL. Down-миграций нет.

Если PostgreSQL недоступен при старте, сервис повторяет попытки с
экспоненциальной задержкой не больше 5 с. Во время работы readiness `/` на
health-порту отвечает 503, пока БД не отвечает; `/live` ничего не проверяет и
остаётся 200, так что оркестратор выводит под из ротации, а не перезапускает его.

## Аудит

- Эмитится core для каждой операции (`GenerateCode`, `Plugins`, `CreatePlugin`,
  `UpdatePlugin`, `DeletePlugin`), включая ошибки.
- `easyp_operations_total{operation,status}` считается в любой редакции.
- Строки пишутся только с лицензией Enterprise; иначе
  `easyp_audit_events_skipped_total` считает то, что не записано.
- Записи идут через ограниченную очередь (`audit.buffer_size`, 1000) к пакетному
  писателю (`audit.batch_size`, `audit.flush_interval`). Запись, не нашедшая
  места за `audit.enqueue_timeout` (1 с), отбрасывается и считается в
  `easyp_audit_events_lost_total{reason="enqueue_timeout"}`. Сама операция при
  этом успешна: аудит никогда не валит запрос.
- Партиции на `audit.pre_create_months` вперёд создаются каждые
  `audit.partition_check_interval`; партиции старше `audit.retention_months`
  удаляются.

## Одна реплика [#single-replica]

Кеш плагинов на диске нельзя делить между процессами: распаковка заканчивается
удалением и переименованием, которые сериализует только блокировка внутри
процесса, а `cache_max_bytes` каждый процесс считает сам. Helm-чарт запускает
одну реплику с томом `ReadWriteOnce` и стратегией `Recreate`. Он *разрешает*
`replicaCount > 1` с томом `ReadWriteMany`; такая комбинация не поддерживается и
портит кеш при одновременных промахах. Сторона БД безопасна для нескольких
процессов (миграции и обслуживание партиций берут блокировки) — именно поэтому
перезапуск на новую версию безопасен.
