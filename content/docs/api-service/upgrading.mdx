## Pin the source and deployment artifact

This reference targets service runtime code at <code>4b01518b42c6f448d21216e3c0e8c35ef66d5c2d</code>. Its latest local release tag is <code>v1.0.2</code> (<code>c28252fffc88324cbfa59c5230edf7fc587e44cb</code>). The changes after that tag affect <code>AGENTS.md</code> and the development Compose healthcheck, not Go runtime code. The chart version is 1.0.2 and its appVersion is v1.0.2. Match a configuration/Compose file to the actual binary rather than assuming <code>latest</code> means current master.

Version tags identify a release by convention; <code>latest</code> moves with releases and <code>edge</code> with successful master builds. A digest or archived binary is the recovery identity. Neither a mutable image tag nor successful image download proves schema compatibility with the database. See [Installation](./installation).

## Database transitions

The server runs embedded Goose migrations forward before becoming ready. The checked tree contains exactly two SQL migrations:

| Database transition | Change | Operational consequence |
| --- | --- | --- |
| Empty database → migration 1 | Creates plugin registrations and the original audit table. | Requires PostgreSQL DDL rights; startup cannot skip the database. |
| Migration 1 → migration 2 | Rebuilds audit as a monthly UTC-partitioned table, copies existing rows, and replaces the old table. | Can take locks and temporarily require additional disk proportional to retained audit data. Test the copy on a restored production-sized snapshot. |

A migration advisory lock coordinates concurrent migration attempts, but it does not make a multi-replica shared plugin cache safe or make every schema change zero-downtime. Liveness starts independently of database readiness so a slow migration is not automatically treated as a dead process. Size startup/readiness probes and shutdown budgets for the actual migration and workload.

## Upgrade procedure

Record the current binary/image digest, configuration, plugin registrations and artifact manifest, PostgreSQL migration version, and active client versions. Create and test a [coordinated backup](./backup). Read the target diff, including its embedded migrations, wire API, config fields, Docker runtime, chart templates, and operator CLI; release notes are an index, not the runtime contract.

Validate the target configuration with the **target** <code>easyp-svc config validate --cfg service.yaml</code>, then inspect <code>config print --origin</code> without revealing secrets. Unknown/removed YAML keys must be migrated rather than ignored. In particular, current code has <code>license.public&#95;keys</code>, not <code>license.public&#95;key</code>, and no configurable <code>db.driver</code>. Set <code>EASYP&#95;CONFIG</code> for the separate healthcheck process when the server uses a file.

In staging, restore the snapshot, provision matching artifacts, and start the target build. Exercise a cold and warm generation for each critical plugin, list/pagination, permitted and rejected authentication, client transport/message limits, and audit when licensed. Compare generated outputs with the old build; compilation of the documentation alone cannot establish generation compatibility.

Schedule a controlled production cutover. The default chart is one replica with a Recreate strategy and a ReadWriteOnce volume, so plan for interruption rather than promising a rolling zero-downtime upgrade. Keep <code>terminationGracePeriodSeconds</code> above the server hard shutdown budget, and that above the generation timeout. Watch migration logs, HTTP readiness, queue/rejection metrics, plugin stderr, and client outcomes before restoring normal traffic.

## Behavior changes to verify explicitly

The present implementation uses text ordering for <code>latest</code>; it does not establish SemVer ordering. Old registrations without a stored archive hash are not automatically repaired by startup or a warm request. <code>plugins register</code> skips existing registrations, so it is not a checksum-backfill command. Prefer new pinned artifact versions, and use a deliberate configuration update only when the cache/artifact consequences are understood.

Enterprise expiry changes runtime feature and registration gating but does not resize an existing pool. License file replacement requires restart. The current developer CLI lacks bearer-token and mTLS support for remote generation; do not roll out <code>auth.require&#95;authentication</code> assuming an <code>EASYP&#95;TOKEN</code> environment variable makes that client compatible. See [Client usage](./client-usage).

## Rollback

There is no operator CLI command to roll back Goose migrations. Although SQL Down sections exist, their existence does not prove that an old binary can safely use the new schema or that reverse migration is lossless for every live dataset. Do not execute a downgrade against the only production copy as a speculative recovery step.

First determine whether rollback is binary-only with a tested compatible schema. Otherwise restore the coordinated pre-upgrade database/artifact recovery set into an isolated deployment using the prior binary, verify it, and switch traffic deliberately. Writes accepted after the backup require an explicit reconciliation or accepted data-loss decision. A Helm rollback changes Kubernetes manifests; it does not restore PostgreSQL, S3 objects, overwritten plugin bytes, or buffered audit events.
