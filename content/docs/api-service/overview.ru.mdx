EasyP API Service запускает плагины генерации кода protobuf на сервере. Клиент
отправляет по gRPC `google.protobuf.compiler.CodeGeneratorRequest` и имя
плагина; сервис запускает этот плагин дочерним процессом и возвращает
`CodeGeneratorResponse`. Разработчикам и CI больше не нужно устанавливать
плагины: они указывают версию, которую оператор один раз зарегистрировал.

Сервис разворачивается у вас. Вы его запускаете, вы решаете, какие плагины в нём
есть, и `.proto`-файлы, из которых идёт генерация, не покидают вашу сеть.

## Какую проблему он решает

- **Версии плагинов расходятся между машинами.** Два разработчика с разными
  сборками `protoc-gen-go` получают из одной схемы разный сгенерированный код, а
  CI — третий.
- **Каждая новая машина — это установка.** Каждый плагин, часто на своём
  языковом тулчейне (Go, Node, JVM, Swift, Python), нужно поставить и держать в
  актуальном состоянии на каждом ноутбуке и раннере.
- **Никто не решает, какие версии разрешены.** Без центрального списка версия
  плагина — та, что кто-то установил последней.

С сервисом версия плагина становится частью конфигурации
(`remote: host/protocolbuffers/go:v1.36.10`), и бинарник за этим именем
одинаков для всех вызывающих.

## Как это работает

```
 разработчик / CI                    EasyP API Service                         хранилища
┌──────────────┐  GenerateCode   ┌──────────────────────────────┐        ┌──────────────────┐
│  easyp CLI   │ ───────────────▶│ gRPC listener (TLS / mTLS)   │        │ PostgreSQL       │
│  или Go SDK  │  имя плагина +  │  rate limit · параллельность │◀──────▶│  реестр плагинов │
│              │  CodeGenerator- │  аутентификация · лицензия   │        │  аудит (Ent.)    │
│              │  Request        │            │                 │        └──────────────────┘
│              │                 │  пул воркеров ─ поиск плагина│        ┌──────────────────┐
│              │                 │            │  (промах кеша) ─┼───────▶│ S3-совместимое   │
│              │                 │  дочерний процесс: плагин    │        │  архивы плагинов │
│              │◀─────────────── │  stdin → stdout              │        └──────────────────┘
└──────────────┘ CodeGenerator-  └──────────────────────────────┘
                 Response
```

1. Клиент локально разбирает `.proto`-файлы и собирает по одному
   `CodeGeneratorRequest` на каждый плагин.
2. Сервис пропускает запрос через ограничение частоты, лимит одновременных
   запросов на клиента, аутентификацию и лицензию и находит плагин по
   `group/name:version` в PostgreSQL.
3. Если настроено объектное хранилище, а плагина нет в локальном кеше, архив
   скачивается, сверяется с sha256, записанным при регистрации, и распаковывается.
4. Плагин запускается дочерним процессом с таймаутом, лимитом размера вывода и
   только тем окружением, которое объявлено в его конфигурации.
5. Ответ возвращается клиенту, и тот записывает файлы.

Полный путь запроса — в [Архитектуре](/ru/docs/api-service/architecture).

## Чем он не является

- **Это не песочница.** Плагины выполняются обычными процессами на хосте
  сервиса. Время, размер вывода, параллельность и окружение ограничены; память,
  CPU, файловая система и сеть — нет. Зарегистрировать плагин — всё равно что
  запустить код на этом хосте. Прочитайте
  [Безопасность](/ru/docs/api-service/security), прежде чем давать кому-то право
  записи.
- **Это не реестр схем.** Он хранит версии плагинов, а не модули `.proto`.
  Зависимостями занимается easyp CLI через Git — см.
  [Менеджер пакетов](/ru/docs/cli/package-manager).
- **Это не публикатор пакетов.** Он возвращает сгенерированные файлы вызывающему
  и не публикует Go-модули, npm- или Maven-пакеты.
- **Он не масштабируется горизонтально.** Одна реплика на том кеша плагинов.
  Масштабируйте, давая поду больше CPU и поднимая лимит генераций.
- **Это не облачный сервис, на который можно зарегистрироваться.** Документация
  описывает ПО, которое разворачиваете вы.

## Когда он нужен

- Код генерируют несколько команд или много CI-раннеров, и результат должен
  совпадать байт в байт.
- Исходники `.proto` не могут покидать вашу сеть, или у сборочной сети нет
  доступа в интернет.
- Нужно точно контролировать, какие плагины и версии можно использовать, включая
  внутренние.
- Вы уже эксплуатируете PostgreSQL, объектное хранилище и Prometheus, и ещё один
  сервис обходится дёшево.

## Когда он не нужен

- Один разработчик или один репозиторий: локальные плагины или встроенные WASM-
  плагины easyp CLI проще.
- Нужны сгенерированные SDK в пакетных менеджерах, облачный реестр схем или
  модель организаций и ролей — см.
  [EasyP и Buf BSR](/ru/docs/api-service/vs-buf-bsr), там перечислено, где BSR
  подходит лучше.
- Вы не можете допустить запуск сторонних бинарников плагинов на хосте внутри
  своей сети без песочницы и не можете изолировать этот хост сами.

## Редакции

Обе обслуживает один и тот же бинарник. Без лицензии он работает как
**Community**: всё, кроме журнала аудита, с потолками в 4 воркера поиска,
10 зарегистрированных версий плагинов и 16 одновременных генераций. Лицензия
**Enterprise** добавляет журнал аудита и снимает потолки. Подробности —
[Аутентификация и лицензирование](/ru/docs/api-service/authentication-and-licensing).

Исходный код сервиса распространяется под Elastic License 2.0; gRPC-контракт
(`api/`) и Go SDK (`sdk/`) — под Apache-2.0.
