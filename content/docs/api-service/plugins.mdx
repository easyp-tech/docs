## Catalog versus installed registrations

The checked <code>service/registry</code> source contains **80 plugin identities, 1,743 version entries, and 10 vendor groups**. These are build recipes, not a claim that every version has been built, runs on every platform, or is already registered on your server. Community can register only ten version rows at once. <code>Plugins</code> lists installed database registrations, not every recipe in Git.

Count from the service repository root with Python and PyYAML:

~~~sh
python3 - <<'PY'
from pathlib import Path
import yaml
files = sorted(Path('registry').rglob('plugin.yaml'))
print('plugins:', len(files))
print('versions:', sum(len(yaml.safe_load(p.read_text()).get('versions', [])) for p in files))
print('vendors:', len({p.relative_to('registry').parts[0] for p in files}))
PY
~~~
## Build, upload, register

<code>plugins build</code> reads one <code>registry/&lt;group&gt;/&lt;name&gt;/plugin.yaml</code>, its Dockerfile, and the selected version entries. It passes <code>VERSION</code> plus configured build arguments to Docker BuildKit and exports the final filesystem into <code>&lt;output&gt;/&lt;group&gt;/&lt;name&gt;/&lt;version&gt;</code>. The resulting **<code>plugin</code> must be a regular file**; the builder makes it executable. It does not execute the plugin, verify its reported version, or recreate the image's entrypoint/user/filesystem isolation at generation time.

~~~sh
easyp-svc plugins build --filter 'protocolbuffers/go:v1.36.11' \
  --output plugins --parallel 1 registry
easyp-svc plugins pack --out packed plugins
~~~
The archive contains the whole version directory, including sidecars. For S3, the order is **build → push → register**; <code>pack</code> is an optional intermediate representation. Use a configured <code>plugins push</code> or its S3 flags, then a bearer-authenticated <code>plugins register</code> using the same selected versions and the server's <code>--plugins-prefix</code>. See the exact options in [Operator CLI](./operator-cli).

For local-only storage, copy the entire built tree to the server's configured <code>plugins&#95;dir</code> and then register it. No upload is required when S3 is disabled. On a different architecture, a successful Docker export does not establish that the destination host can execute the binary.

## Adding a plugin

Create a directory for its stable group/name and a <code>plugin.yaml</code> with a <code>versions</code> sequence. Entries can be a version string or an object with <code>version</code>, <code>build&#95;args</code>, <code>dockerfile</code>, <code>args</code>, and <code>skip</code>. Top-level <code>build&#95;args</code>, <code>dockerfile</code>, and <code>args</code> provide build defaults; version-specific values override them. Build arguments belong to Docker's build, not to Protobuf generation parameters.

~~~yaml
versions:
  - version: v1.36.11
~~~
Use the existing <code>registry/protocolbuffers/go/Dockerfile</code> as a small single-binary example: consume <code>ARG VERSION</code>, build the requested upstream version, and put the final executable at <code>/plugin</code>. If a runtime or adjacent data is required, export it as sidecar files and make the wrapper locate its own directory. **Absolute paths such as <code>/app</code> or <code>/nodejs</code> refer to the service host/container root, not to the exported plugin directory.** Docker <code>ENTRYPOINT</code>, <code>USER</code>, and final-image root layout are not replayed by the process runner.

Test the executable using a real serialized <code>CodeGeneratorRequest</code> on the actual target OS/runtime, verify <code>CodeGeneratorResponse</code> and its error field, and compile the output. Confirm the selected version really changes the executable. A build-only check cannot catch an ignored VERSION argument, missing interpreter, wrong libc, or an absolute wrapper path. Decide which administrators may deploy this code using [Security](./security).

## Known catalog limitations in this snapshot

<code>registry/bufbuild/es/plugin.yaml</code> lists many versions, while its <code>package.json</code> fixes <code>@bufbuild/protoc-gen-es</code> to **2.9.0** and its Dockerfile runs <code>npm ci</code> without selecting the requested VERSION. Both package files match the Buf catalog's v2.9.0 files byte-for-byte. Therefore the recipe does not establish the advertised version for other entries. Its wrapper also invokes <code>/nodejs/bin/node</code> and <code>/app/protoc-gen-es.js</code>, absolute paths that are not automatically relocated by this service. Do not treat those entries as validated working versions; review/fix the recipe separately before use.

More generally, the service repository contains adapted third-party packaging. A directory named <code>bufbuild</code> identifies the upstream publisher, not proof of Buf endorsement or a license exception. Preserve applicable upstream license/copyright and modification notices when redistributing copied recipes and binaries. The [Buf plugin repository license](https://github.com/bufbuild/plugins/blob/392d085396a7b53cf130aed7bd3ee83f22927aa3/LICENSE), checked 2026-09-23, is Apache-2.0; individual generated executables can have different upstream licenses. This documentation does not alter source licenses or certify compliance.

## Why force replacement is dangerous

<code>build --force</code> rebuilds local outputs; <code>pack --force</code> replaces local archives; <code>push --force</code> replaces an existing S3 object. None means “update the server's registered checksum and every replica's cache.” Registration skips <code>AlreadyExists</code>, and warm cache entries are not invalidated by metadata updates.

Prefer publishing a new immutable version. If a same-version repair is unavoidable, freeze consumers, back up the metadata and artifact, replace it through an explicit reviewed update, invalidate each affected cache during controlled maintenance, and test both cold and warm generation. A naked <code>push --force</code> followed by <code>register</code> can leave old warm bytes and new cold checksum failures. See [Architecture](./architecture) and [Backup](./backup).
