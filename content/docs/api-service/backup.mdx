## What must be recoverable

PostgreSQL holds registrations, plugin configuration (including recorded archive hashes), and audit data. It does not contain plugin executables or generated files. In local-only mode, <code>registry.plugins&#95;dir</code> is authoritative and must be backed up. With S3, the bucket/prefix is authoritative and the local directory is a rebuildable cache **only when every needed object and matching registration are recoverable**.

Keep a coordinated recovery set: a database dump/snapshot, plugin artifacts at the matching versions/hashes, the exact server image digest or binary, configuration, the trusted license public keys, and references to recoverable secrets/certificates in your secret-management system. Telemetry stores have independent retention and backup requirements. A PostgreSQL-only backup is not a complete service backup.

## Create a consistent backup

Freeze plugin registrations, updates, deletes, and object replacements for the snapshot window. Because a version can be overwritten and deletion spans different stores without a shared transaction, copying S3 before or after PostgreSQL is not by itself a consistency guarantee. For the strongest simple procedure, stop generation and administration, let the service drain, and then snapshot both stores. Audit generated during the window otherwise needs an explicit recovery-point policy.

A PostgreSQL custom-format dump can be created and inspected with compatible PostgreSQL tools:

~~~sh
pg_dump --dbname="$DB_POSTGRES_DSN" --format=custom --file=easyp.dump
pg_restore --list easyp.dump > easyp.dump.contents.txt
~~~
For local-only artifacts, archive the complete directory, preserving executable modes, symlinks, and sidecars; copying only the entrypoint is insufficient:

~~~sh
tar -C "$PLUGINS_DIR" -czf plugins.tar.gz .
~~~
For S3, use your storage system’s versioning/snapshot or an artifact copy manifest that records object keys and versions/hashes. Include <code>prefix/group/name/version/plugin.tgz</code>. An uncoordinated <code>sync</code> to a newer bucket can lose deleted objects or replace bytes under an existing version. Encrypt and access-control backup sets; registration configuration and audit can contain sensitive data. Record checksums and test that the dump can be read before declaring the backup successful.

## Restore into an isolated deployment

Create an empty compatible PostgreSQL database and restore the selected snapshot with a role that will own the restored objects. Do not point this procedure at a live production database:

~~~sh
pg_restore --dbname="$RESTORE_POSTGRES_DSN" \
  --no-owner --no-privileges --exit-on-error easyp.dump
~~~
Restore the matching plugin tree or S3 object versions, configuration, and independently managed credentials. Use the original server build first; starting a newer build automatically applies its embedded forward migrations. In S3 mode, a fresh private cache is useful for a recovery test because warm files can conceal missing objects or checksum mismatches. In local-only mode, an empty cache directory is not recoverable automatically.

Keep restored workers disconnected from production clients and from any production audit/metadata database while testing. Check registration counts and selected exact versions, HTTP readiness, one cold generation per critical plugin, a repeated warm generation, and the output files expected by the consuming build. Verify Enterprise audit recording and retention only with a valid authorized license; a successful Community generation does not validate Enterprise recovery.

## Recovery limits

There is no built-in backup scheduler, cross-store point-in-time transaction, durable audit queue, or audit replay. The latest buffered events can be lost at a crash even when a database backup is current. Recovery time depends on restore size, plugin downloads, database performance, and the number of critical versions to validate; this documentation does not promise an RPO or RTO. Exercise the restore procedure using your actual artifact set and record the measured result. See [Upgrading](./upgrading) and [Runbooks](./runbooks).
