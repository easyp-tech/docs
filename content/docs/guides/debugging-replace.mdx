title: "Debugging with Replace Directives"
description: "Use local module replacements for development and understand their lockfile and network limits."
---

A local <code>replace</code> in <code>protobuf.mod</code> lets you edit a dependency alongside its consumer without publishing each intermediate change.

## Setting Up a Local Replace

Suppose <code>proto/user</code> requires <code>github.com/acme/weather</code>. Put the dependency checkout at <code>proto/weather-fork</code>, next to <code>proto/user</code>, and add:

~~~protobuf
// proto/user/protobuf.mod
module github.com/acme/user

require (
    github.com/acme/weather v1.2.3
)

replace github.com/acme/weather => ../weather-fork
~~~

The relative replacement path is resolved from the directory containing this <code>protobuf.mod</code>, so it points to <code>proto/weather-fork</code>, regardless of the shell's working directory. Keep the replacement's module roots and imports valid.

## Local Development Workflow

With a generator file in <code>proto/user</code>, run from the repository root:

~~~bash
easyp generate --project ./proto/user
~~~

Generation uses the replacement's local sources for the replaced dependency. You can iterate on both schemas without publishing a new dependency tag for every edit.

<Callout type="info">
Dependency downloads are unnecessary only when the whole dependency graph is local or already in verified cache. One local replacement does not make unreplaced dependencies or their transitive imports local. Required remote dependencies still need valid locks and may need downloads; remote plugins still need network access.
</Callout>

## Reproducible Lock Guardrail

<Callout type="warn">
<code>easyp mod tidy</code> and <code>easyp mod update</code> explicitly reject active local replacements, even when generation can run with them. Remove the replacements before resolving a reproducible dependency lock.
</Callout>

These are mutating dependency commands, not read-only CI checks. Use <code>easyp mod download</code> to install and verify an already prepared lock; it is not a blanket check forbidding local replacements. Review the manifest before release.

### Preparing for PR Submission

1. Publish the dependency changes in Git at the intended version.
2. Update <code>require</code> in the consumer's <code>protobuf.mod</code>.
3. Remove the <code>replace</code> directive.
4. Run <code>easyp mod tidy</code> in that module to update <code>protobuf.lock</code>.
5. Regenerate the selected project, run consumer tests, and commit the reviewed manifest, lock, and generated changes.

For breaking checks, replacements inside the Git repository use each revision's own contents. External local replacements are rejected because the baseline has no recoverable historical copy. See [breaking checks](/docs/cli/breaking-changes).
