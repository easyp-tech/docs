---
title: "Breaking-проверки в CI"
description: "Запуск проверки совместимости EasyP v1 относительно доступной локально Git-базы в CI."
---

Проверка v1 сравнивает текущие <code>.proto</code> с Git-ревизией. Для репозитория со схемами в <code>proto</code> сохраните эту политику в корневом <code>easyp.yaml</code>:

~~~yaml
version: v1
breaking:
  baseline: git:origin/main
  categories: [FILE]
  ignore_unstable: false
  ignore: [proto/experimental]
~~~

Поддерживаются все четыре профиля совместимости на базе дескрипторов: <code>FILE</code>, <code>PACKAGE</code>, <code>WIRE_JSON</code> и <code>WIRE</code>. Несколько профилей применяются совместно; если <code>categories</code> не задан или пуст, по умолчанию используется <code>["FILE"]</code>. Задавайте <code>ignore_unstable: true</code>, только если нужно пропускать пакеты с поддерживаемыми нестабильными суффиксами версий; матрица профилей и точные формы описаны в [справочнике breaking-проверок](/ru/docs/cli/breaking-changes).

Путь исключения отсчитывается от файла, задающего эффективную секцию <code>breaking</code>. В <code>proto/easyp.yaml</code> тот же каталог задавался бы как <code>ignore: [experimental]</code>. Изменение <code>--root</code> не меняет эту базу.

## Запуск проверок

Из корня репозитория с закоммиченным lock-файлом используйте <code>--frozen</code> в CI, чтобы EasyP проверял сохранённый граф без изменения файлов и запрещал локальные замены:

~~~bash
easyp validate-config
easyp mod download --frozen
easyp lint --frozen --path proto
easyp breaking --frozen --path proto
~~~

<code>mod download --frozen</code> проверяет коммиты и хеши содержимого из <code>protobuf.lock</code>. Breaking-проверка использует собственные манифесты, lock-файлы и зависимости каждой ревизии; для базы могут потребоваться дополнительные загрузки. Храните манифесты и lock-файлы в репозитории и разрешайте обновления зависимостей до проверки в CI.

## Доступность базовой ревизии

Базой может быть ветка, лёгкий или аннотированный тег, полный SHA коммита или другая разрешимая локально Git-ревизия, например <code>HEAD</code>. Сначала получите нужные ссылки и объекты. Короткое имя ветки приоритетнее одноимённого тега; для явного выбора тега используйте <code>refs/tags/v1.2.0</code>.

Явный <code>--against</code> перекрывает <code>breaking.baseline</code>; без обоих значений используется <code>master</code>. Передавайте ссылку прямо во флаг, без <code>git:</code> и <code>git-ref=</code>.

После установки EasyP v1 (из архивов релизов, Homebrew или образа `ghcr.io/easyp-tech/easyp:v1.0.0`) эти шаги GitHub Actions сравнят схемы с базовым коммитом pull request:

~~~yaml
- uses: actions/checkout@v4
  with:
    fetch-depth: 0
- name: Check protobuf compatibility
  env:
    BASE_REF: ${{ github.event.pull_request.base.sha }}
  run: easyp breaking --frozen --path proto --against "$BASE_REF"
~~~

Используйте фрагмент в job для <code>pull_request</code>. Полная история обеспечивает доступность базы в обычном checkout PR; отсутствие ревизии завершает проверку ошибкой, а не выбирает другую базу. См. полный [workflow GitHub Actions](/ru/docs/ci-cd/github-actions).
