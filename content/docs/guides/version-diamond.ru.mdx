**Ромбовидная зависимость** возникает, когда прямые и транзитивные требования задают разные версии одного модуля. EasyP использует MVS для выбора версии внутри графа зависимостей каждого модуля.

---

## Описание сценария

Рассмотрим модуль сервиса <code>user</code>, который зависит от двух пакетов: <code>common</code> и <code>weather</code>.

- <code>user</code> напрямую требует <code>common v1.2.0</code>.
- <code>user</code> напрямую требует <code>weather v2.1.0</code>.
- <code>weather v2.1.0</code> транзитивно требует <code>common v1.3.0</code>.

~~~text
               +-------------------+
               |    proto/user     |
               +---------+---------+
                         |
           +-------------+-------------+
           |                           |
           v                           v
+---------------------+     +---------------------+
| github.com/acme/    |     | github.com/acme/    |
| common v1.2.0       |     | weather v2.1.0      |
+---------------------+     +----------+----------+
                                       |
                                       v
                            +---------------------+
                            | github.com/acme/    |
                            | common v1.3.0       |
                            +---------------------+
~~~

---

## Правило выбора MVS

Для семантических требований к одному модулю MVS выбирает наибольший из запрошенных минимумов:

<code>Итоговая версия = max(Запрошенных минимумов)</code>

1. **Сбор требований**: <code>[ v1.2.0 (от user), v1.3.0 (от weather) ]</code>
2. **Выбор максимума**: <code>max(v1.2.0, v1.3.0) = v1.3.0</code>
3. **Результат**: Для графа модуля выбирается <code>common v1.3.0</code>.

MVS выбирает <code>v1.3.0</code> по этим требованиям, но не проверяет компиляцию потребителей. Семантические версии выражают намерение сопровождающих и не доказывают совместимость схем или сгенерированного кода. Отдельные корневые модули разрешаются независимо и могут выбрать разные версии.

---

## Что если возникло ломающее изменение?

При несовместимой выбранной версии граф может успешно разрешиться, а генерация или тесты потребителей — упасть. Перед релизом запускайте <code>easyp breaking</code> относительно подходящей доступной базы, затем тестируйте сгенерированные клиенты. Проверка охватывает реализованные правила и настроенную область; она не гарантирует совместимость каждого потребителя.

Пример максимума из минимумов относится к семантическим версиям. Разные точные коммиты конфликтуют. Точный коммит может сосуществовать с семантическими требованиями, только если выбранный тег указывает на тот же коммит. См. [разрешение зависимостей](/ru/docs/architecture/mvs-dependency-resolution).
