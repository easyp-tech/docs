В данном руководстве рассматривается процесс добавления сторонних или общих Protobuf-модулей в проект EasyP.

---

## Добавление модуля через `easyp get`

Из каталога, в котором лежит ваш `protobuf.mod`, выполните:

```bash
easyp get github.com/acme/weather
# Укажите SemVer-тег, не-SemVer Git-тег или полный Git-коммит:
easyp get github.com/acme/weather@v1.2.3
easyp get github.com/acme/weather@release-2026-10
# Задайте проверенный корень импортов для зависимости без метаданных корней:
easyp get --import-root api/proto github.com/acme/legacy-schemas@v1.0.0
```

Команда добавляет выбранный модуль как прямой `require`, записывает его транзитивные зависимости с пометкой `// indirect` и обновляет `protobuf.lock` с точными коммитами и хешами содержимого. Именованные не-SemVer Git-теги (`@<тег>`) предварительно разрешаются в полный SHA коммита до записи в `protobuf.mod`. Вложенный модуль указывают по полному пути, например `github.com/acme/contracts/proto/user`. Тег необязателен: без него EasyP закрепляет текущий HEAD репозитория. Для каждого локального модуля с собственным `protobuf.mod` запускайте команду в его каталоге.

Добавьте нужный protobuf `import` в `.proto`, затем проверьте и закоммитьте `protobuf.mod` и `protobuf.lock`.

Ниже приведён эквивалентный способ с ручным редактированием манифеста.

---

## Общий процесс

1. **Объявление зависимости**: Добавление Git-модуля в `protobuf.mod`. Через `import` в `.proto` используются файлы объявленной зависимости.
2. **Запуск резолюции**: Выполнение `easyp mod tidy` после ручного изменения манифеста для вычисления полного графа транзитивных зависимостей.
3. **Фиксация в Git**: Проверка и коммит обновлённых файлов `protobuf.mod` и `protobuf.lock`.

---

## Шаг 1: Ручное объявление зависимости

Откройте `protobuf.mod` вашего модуля и добавьте требуемый модуль в блок `require`:

```protobuf
// proto/user/protobuf.mod
module github.com/acme/contracts/proto/user

roots proto

require (
    github.com/googleapis/googleapis 03a91044136a014466d4293eb1fe91f2b02075d2
    github.com/acme/weather v1.2.3
)
```

После этого импортируйте файл зависимости в Protobuf-файле:

```protobuf
// proto/user/v1/user.proto
syntax = "proto3";

package user.v1;

import "google/type/datetime.proto";
```

---

## Шаг 2: Выполнение `easyp mod tidy`

Запустите команду `easyp mod tidy` в терминале:

```bash
easyp mod tidy
```

### Что делает `easyp mod tidy`:
- Сканирует все `.proto` файлы модуля для поиска активных `import`.
- Загружает метаданные требуемых модулей из Git-репозиториев.
- Вычисляет Minimal Version Selection (MVS) для транзитивных зависимостей.
- Дописывает транзитивные зависимости в `protobuf.mod` с пометкой `// indirect`.
- Генерирует или обновляет `protobuf.lock` с хешами коммитов и контрольными суммами.

### Git-репозитории с конфигурацией Buf или старого EasyP

Проект-потребитель по-прежнему объявляет Git-источник через `require`. Репозиторий зависимости может использовать другой формат:

- EasyP v1 `protobuf.mod`: читаются `roots` и `require`.
- Buf v2 `buf.yaml`: читаются `modules[].path`, а также фильтры `modules[].includes` и `modules[].excludes`.
- Buf v1 `buf.work.yaml`: читаются `directories` и `build.excludes` вложенных `buf.yaml`; одиночный модуль с `buf.yaml` v1 использует `.` и `build.excludes`.
- Buf v1beta1 `buf.yaml`: читаются `build.roots` (по умолчанию `.`) и `build.excludes`.
- Старый EasyP: из прежнего `protobuf.mod` читаются зависимости `direct`, а из `easyp.yaml` — локальные `generate.inputs[].directory.root` и Git-входы.

Если в старой зависимости EasyP у Git-зависимости не указана версия, `mod tidy` разрешает HEAD Git-репозитория и фиксирует его коммит в v1 lock. Тег не нужен. Старый формат EasyP `source@<commit>` также читается транзитивно.

Если Git-зависимость на Buf объявляет `deps` из BSR, встроенный `bsr.StaticResolver` сопоставляет **5 популярных BSR-модулей** (`buf.build/googleapis/googleapis`, `buf.build/grpc-ecosystem/grpc-gateway`, `buf.build/mercari/grpc-federation`, `buf.build/envoyproxy/protoc-gen-validate` и `buf.build/bufbuild/protovalidate`) с зафиксированными Git-снимками и сохраняет привязку в `modules[].bsr` файла `protobuf.lock`. Неизвестные BSR-модули вызывают явную ошибку (Git URL не угадывается), а прямые BSR-зависимости в `protobuf.mod` потребителя не поддерживаются.

Обновлённый `protobuf.mod` (нативные модули v2+ требуют суффикс мажорной версии `/v2` в пути модуля):

```protobuf
// proto/user/protobuf.mod
module github.com/acme/contracts/proto/user

roots proto

require (
    github.com/googleapis/googleapis 03a91044136a014466d4293eb1fe91f2b02075d2
    github.com/acme/weather v1.2.3
    github.com/grpc-ecosystem/grpc-gateway/v2 v2.19.0 // indirect
)
```

---

## Шаг 3: Коммит изменений

Всегда коммитьте файлы `protobuf.mod` и `protobuf.lock` в репозиторий. Это гарантирует, что все разработчики и CI-пайплайны будут использовать идентичные версии схем:

```bash
git add protobuf.mod protobuf.lock
git commit -m "feat: add googleapis and weather dependencies"
```
