The **diamond dependency problem** occurs when direct and transitive requirements request different versions of the same module. EasyP uses MVS to select a version within each module's dependency graph.

---

## Scenario Description

Consider a service module <code>user</code> that relies on two dependencies: <code>common</code> and <code>weather</code>.

- <code>user</code> explicitly requires <code>common v1.2.0</code>.
- <code>user</code> explicitly requires <code>weather v2.1.0</code>.
- <code>weather v2.1.0</code> transitively requires <code>common v1.3.0</code>.

~~~text
               +-------------------+
               |    proto/user     |
               +---------+---------+
                         |
           +-------------+-------------+
           |                           |
           v                           v
+---------------------+     +---------------------+
| github.com/acme/    |     | github.com/acme/    |
| common v1.2.0       |     | weather v2.1.0      |
+---------------------+     +----------+----------+
                                       |
                                       v
                            +---------------------+
                            | github.com/acme/    |
                            | common v1.3.0       |
                            +---------------------+
~~~

---

## The MVS Resolution Rule

For semantic-version requirements on the same module, MVS selects the highest requested minimum:

<code>Resolved Version = max(Requested Minimums)</code>

1. **Collect requested minimums**: <code>[ v1.2.0 (from user), v1.3.0 (from weather) ]</code>
2. **Select maximum**: <code>max(v1.2.0, v1.3.0) = v1.3.0</code>
3. **Outcome**: <code>common v1.3.0</code> is selected for the module resolution graph.

MVS selects <code>v1.3.0</code> from these requirements; it does not test whether either consumer compiles. Semantic version labels express maintainer intent and do not prove schema or generated-code compatibility. Separate root modules resolve independently and can select different versions.

---

## What If Breaking Changes Occur?

If the selected version is incompatible, the graph can resolve successfully while generation or consumer tests fail. Run <code>easyp breaking</code> against an appropriate available baseline before release, then test generated clients. The checker covers its implemented rules and configured scope; it cannot guarantee every consumer remains compatible.

This maximum-of-minimums example applies to semantic versions. Different exact commit requirements conflict. An exact commit can coexist with semantic-version requirements only when the selected tag resolves to that same commit. See [dependency resolution](/docs/architecture/mvs-dependency-resolution).
