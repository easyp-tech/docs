---
title: "Multi-Target Code Generation"
description: "Select independent backend and frontend generation projects that consume the same protobuf modules."
---

Go services and TypeScript clients can consume the same Protocol Buffer schemas while keeping separate <code>easyp.gen.yaml</code> files. Dependency identities and requirements belong in <code>protobuf.mod</code>; resolved dependency commits and hashes belong in <code>protobuf.lock</code>.

## Project Architecture & Configuration

This example has modules at <code>proto/user</code> and <code>proto/order</code>, each with its own <code>protobuf.mod</code>. The backend selects both modules; the frontend selects only the user module. Paths in <code>generate.modules</code> are relative to the repository root.

### Backend project

~~~yaml
# backend/easyp.gen.yaml
version: v1
generate:
  modules:
    - proto/user
    - proto/order
plugins:
  - name: go
    out: ./gen/go
    opts:
      paths: source_relative
  - name: go-grpc
    out: ./gen/go
    opts:
      paths: source_relative
      require_unimplemented_servers: false
options:
  go:
    package_prefix: github.com/acme/app/backend/gen/go
~~~

Install the required <code>protoc-gen-go</code> and <code>protoc-gen-go-grpc</code> executables in the build environment. Control their versions there; a local plugin cannot declare <code>version</code> in this file.

### Frontend project

~~~yaml
# frontend/easyp.gen.yaml
version: v1
generate:
  modules:
    - proto/user
plugins:
  - name: es
    out: ./src/gen
    opts:
      target: ts
~~~

This project requires <code>protoc-gen-es</code> on <code>PATH</code>. Output directories are relative to the project file, so backend and frontend output stay separate. Give modules distinct proto-relative output paths if they share an output directory.

### Shared Go option

An ancestor generator file can supply a Go package prefix:

~~~yaml
# easyp.gen.yaml at the repository root
version: v1
options:
  go:
    package_prefix: github.com/acme/app/gen/go
~~~

The nearest explicit <code>options.go.package_prefix</code> wins. The backend above overrides this value. This inheritance does not copy <code>generate</code> or <code>plugins</code> into child projects. The prefix sets <code>go_package</code>; full managed mode is configured separately through <code>generate.managed</code>.

## Key Configuration Elements

- <code>generate.modules</code> selects complete local modules or canonical module identities available in the selected dependency context. With no list, generation uses the nearest enclosing module, or the project directory when no manifest exists.
- <code>generate.packages</code> selects exact protobuf package names, not prefixes or globs. Empty selects all source files.
- Each plugin selects exactly one source: <code>name</code>, <code>path</code>, <code>command</code>, or <code>remote</code>, and requires <code>out</code>.
- <code>opts</code> accepts a map or a list of option strings. <code>with_imports: true</code> also generates transitive imports for that plugin.

## Plugin Execution Sources

| Source | Version control |
| --- | --- |
| <code>name</code> | Uses the installed executable; supported built-in names fall back to bundled WASM when no matching executable is on PATH. Pin the build environment and EasyP binary. |
| <code>path</code> or <code>command</code> | Uses the executable you provide. Manage its version outside the generator YAML. |
| <code>remote</code> | Requires a separate pinned semantic <code>version</code>; do not embed the version in the remote name. |

Local and bundled plugins reject a nonempty <code>version</code> because EasyP cannot verify it against the executable. Remote execution requires network access. Neither WASM nor a remote version pin alone guarantees identical output bytes.

## Execution Workflow

From the repository root, select the projects explicitly:

~~~bash
easyp generate --project ./backend --project ./frontend
~~~

Or recursively select every project below the working directory:

~~~bash
easyp generate --all
~~~

Do not combine <code>--all</code> and <code>--project</code>. Without either flag, <code>easyp generate</code> selects the nearest enclosing <code>easyp.gen.yaml</code>; it does not recurse through child projects.

Projects selecting the same module use that module's manifest and dependency lock. Separate modules can have different dependency graphs, so review their locks and test the generated clients together.

## Profiles for one module

For a module containing <code>private.v1</code> and <code>public.v1</code> packages, keep both profiles in the module directory beside <code>protobuf.mod</code>. Its roots and dependencies apply to both profiles.

~~~yaml
# private.easyp.gen.yaml
version: v1
generate:
  packages: [private.v1]
plugins:
  - name: go
    out: ./gen/go
    opts:
      paths: source_relative
options:
  go:
    package_prefix: github.com/acme/app/gen/go
~~~

~~~yaml
# public.easyp.gen.yaml
version: v1
generate:
  packages: [public.v1]
plugins:
  - name: go
    out: ./gen/go
    opts:
      paths: source_relative
options:
  go:
    package_prefix: github.com/acme/app/gen/go
~~~

Run each profile from that directory:

~~~bash
easyp generate --gen-config private.easyp.gen.yaml
easyp generate --gen-config public.easyp.gen.yaml
~~~

The selected packages become generation targets; required imports remain available for linking. Each file keeps the usual module-relative source filters and file-relative plugin outputs, so changing the filename requires no path adjustments. These profiles explicitly repeat the Go prefix: a standard <code>easyp.gen.yaml</code> in the same directory is independent. Only standard files in ancestor directories provide inherited options.

<code>--gen-config</code> selects one file and cannot be combined with <code>--project</code> or <code>--all</code>. Recursive discovery continues to look for standard <code>easyp.gen.yaml</code> files. Use separate commands to run multiple named profiles.
