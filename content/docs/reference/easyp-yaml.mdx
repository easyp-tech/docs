title: "easyp.yaml Reference"
description: "Complete specification for easyp.yaml, configuring producer-side linting rules, breaking change detection, path exclusions, and policy inheritance."
---

<code>easyp.yaml</code> defines lint and compatibility policies for protobuf schemas. Each section uses its nearest definition in the directory tree. Explicit <code>linters.extends</code> and <code>breaking.extends</code> inherit section-scoped bases from bounded local files or declared, locked modules. See [shared policies](/docs/guides/organization-lint-style).

## Example configuration

~~~yaml
version: v1
linters:
  default: STANDARD
  enable: [ENUM_VALUE_PREFIX, RPC_REQUEST_RESPONSE_UNIQUE]
  disable: [PACKAGE_VERSION_SUFFIX]
  allow_comment_ignores: true
linters-settings:
  ENUM_ZERO_VALUE_SUFFIX:
    suffix: UNSPECIFIED
  SERVICE_SUFFIX:
    suffix: Service
issues:
  exclude-rules:
    - path: legacy/**/*.proto
      linters: [FIELD_LOWER_SNAKE_CASE]
    - path: generated
breaking:
  baseline: git:main
  categories: [FILE]
  ignore_unstable: true
  ignore: [gen]
~~~

## Section cascading

The <code>linters</code>, <code>linters-settings</code>, <code>issues</code>, and <code>breaking</code> sections each come as a whole from the nearest file defining that section; fields are not partially merged. A child <code>issues: &#123;&#125;</code> clears inherited exclusions. An inherited exclusion path stays relative to the file defining <code>issues</code>, even when the invocation directory or <code>--root</code> is deeper.

Policy discovery searches ancestors within the workspace. If no ancestor policy exists, one unambiguous outermost descendant policy may be selected; multiple independent policies require explicit <code>--cfg</code>. Explicit <code>--cfg</code> takes precedence, and explicit <code>--root</code> supplies the default lookup start.

## Rule selection and exclusions

Repeated rule or group names are idempotent, and disabling wins over enabling. Unknown names in enable, disable, and exclusions are errors even if also listed on the opposite side. The reserved <code>PACKAGE_NO_IMPORT_CYCLE</code> rule is unimplemented and cannot be selected.

<code>issues.exclude-rules[].path</code> uses <code>/</code> separators and is anchored to the directory of the file supplying the effective <code>issues</code> section:

| Pattern | Matches |
| --- | --- |
| <code>generated</code> | The directory and its whole subtree |
| <code>api/file.proto</code> | That file |
| <code>api/&#42;.proto</code> | Files directly inside api |
| <code>api/?.proto</code> | One character before .proto |
| <code>api/[a-c].proto</code> | a.proto, b.proto, or c.proto |
| <code>api/&#42;&#42;/file.proto</code> | Zero or more intermediate directories |

<code>&#42;&#42;</code> must occupy an entire segment. Absolute paths, backslashes, <code>..</code> traversal, and malformed patterns are rejected. A literal path ending in <code>.proto</code> matches that file only; other literal paths cover their subtree. These rules apply to issue exclusions only, not every configuration path.

Without <code>path</code>, the rule applies to all files covered by the effective issues section. <code>linters</code> accepts implemented rule or group names; an omitted or empty list excludes matching files from linting entirely. A completely empty rule <code>&#123;&#125;</code> retains its explicit all-ignore meaning. In the example, the whole <code>generated</code> subtree is excluded, while only the named rule is suppressed in <code>legacy</code>.

## Comment suppressions

<code>linters.allow_comment_ignores</code> defaults to true per effective policy. False disables comment-based suppressions. <code>easyp:disable</code>/<code>easyp:enable</code> provide annotations or bounded regions; legacy <code>nolint:RULE</code> and <code>buf:lint:ignore RULE</code> remain annotations. Unknown names, empty directives, and unmatched enables remain errors even when suppressions are disabled. See the [linter guide](/docs/cli/linter) for examples and scope.

## Breaking checks

Explicit <code>--against</code> wins over <code>breaking.baseline</code>; without either, the default is <code>master</code>. This includes explicit <code>--against master</code>. An empty explicit flag is an error, and a missing Git baseline does not fall back to the configured one.

The baseline can name a local branch, a lightweight or annotated tag, a full commit SHA, or another locally resolvable Git revision such as <code>HEAD</code>. Required refs and objects must already be present in the checkout. A bare branch name takes precedence over an identically named tag; use <code>refs/tags/v1.2.0</code> to select the tag explicitly. In YAML use <code>git:refs/tags/v1.2.0</code>; for the CLI pass <code>--against refs/tags/v1.2.0</code> without a <code>git:</code> or <code>git-ref=</code> prefix.

<code>breaking.ignore</code> paths are relative to the file supplying the effective <code>breaking</code> section, not the Git root or <code>--root</code>. For example, <code>ignore: [generated]</code> in <code>api/easyp.yaml</code> excludes <code>api/generated</code>, including when that section is inherited. Entries must be nonempty local relative paths; absolute paths and paths escaping the policy directory or repository are rejected.

Each selected module uses revision-local roots, manifests, and locks for its current and baseline revisions. The baseline is read from an isolated Git snapshot; the caller's checkout, manifest, and lock are unchanged. Policies come from current configuration and may each select a different baseline. See the [breaking guide](/docs/cli/breaking-changes) for local replacement limits.

Select FILE for file/source compatibility, PACKAGE to allow moves within a package, WIRE_JSON for binary plus JSON, or WIRE for binary. See the [profile matrix](/docs/cli/breaking-changes). Omitted/empty categories preserve legacy checks. Shared policies remain pinned through the consuming manifest/lock.

## Unstable packages

<code>breaking.ignore_unstable</code> defaults to false. When true, it filters packages by their final protobuf package-name component on both sides of comparison, including dependency packages. Supported forms are <code>vNtest...</code>, <code>vNalpha</code>, <code>vNbeta</code>, <code>vNpMalpha</code>, and <code>vNpMbeta</code>. Alpha/beta may have a positive sequence number; N, M, and that sequence start with 1–9 followed by digits. Test may have any trailing suffix, including none.

For example, <code>acme.v1testFeature</code>, <code>acme.v2alpha3</code>, and <code>acme.v2p3beta</code> are skipped. <code>acme.v1</code>, <code>acme.v0alpha1</code>, <code>acme.v1beta0</code>, and <code>acme.v1beta1.service</code> do not match. Stable packages remain checked, including their references to unstable types. Filtering does not excuse malformed sources: reading and import resolution happen before filtering.
