title: "easyp.gen.yaml Reference"
description: "Complete specification for easyp.gen.yaml, configuring consumer-side code generation, plugin outputs, WASM/remote execution, and managed package options."
---

The `easyp.gen.yaml` file specifies **consumer-side code generation rules**. Residing alongside consuming applications or service projects, it defines which modules to compile, which plugins to invoke, where generated artifacts should be written, and managed options.

In accordance with EasyP's zero-duplication principles, `easyp.gen.yaml` **never** contains dependency URLs or version numbers for Protobuf schemas—schema sources and versions are resolved strictly through `protobuf.mod` and `protobuf.lock`.

## Example Configurations

### Project-Level Generator (`backend/easyp.gen.yaml`)

```yaml
version: v1

generate:
  modules:
    - proto/user
    - proto/order

plugins:
  - name: go
    out: ./gen/go
    opts:
      paths: source_relative
  - name: go-grpc
    out: ./gen/go
    opts:
      paths: source_relative
      require_unimplemented_servers: false

options:
  go:
    package_prefix: github.com/acme/backend/gen/go
```

### Remote Web Generator (`frontend/easyp.gen.yaml`)

```yaml
version: v1

generate:
  modules:
    - proto/user

plugins:
  - remote: gen.easyp.tech/es
    version: v2.0.0
    out: ./src/gen
    opts:
      target: ts
```

## Managed Options (`options`)

Instead of requiring explicit file-level options (like `option go_package = "..."`) inside every individual `.proto` schema file, EasyP's managed `options` block groups settings logically by target language.

For example, setting `options.go.package_prefix: github.com/acme/backend/gen/go` automatically computes import paths based on the module directory layout without mutating source `.proto` files.

The existing managed-mode rules remain available under `generate.managed`. For example, a package-specific override can be written as:

```yaml
version: v1
generate:
  managed:
    enabled: true
    override:
      - file_option: go_package_prefix
        package: user.v1
        value: github.com/acme/backend/gen/user
plugins:
  - name: go
    out: ./gen/go
```

A repository-root `easyp.gen.yaml` may provide `options.go.package_prefix` as a default for nested generator files. Nested `generate.managed` rules take precedence over that inherited default. A prefix declared in the same generator file has the highest priority. Plugin lists stay local to each generator file.

The current v1 generator selects complete modules. `generate.packages` is reserved for a later release, once its matching syntax is specified.

Remote plugins require a `version` such as `v2.0.0`. EasyP sends that exact version to the remote generator. For local `protoc-gen-*` executables and bundled WASM plugins, the executable selected at runtime determines the version; the separate `version` field is rejected because EasyP cannot verify it.

Each plugin declares exactly one source: `name`, `path`, `command`, or `remote`. Use `path` for a specific binary and `command` for an executable plus arguments. Both run from the directory where `easyp generate` starts and, like any Protobuf plugin, must read a `CodeGeneratorRequest` from stdin and write a `CodeGeneratorResponse` to stdout.

```yaml
version: v1
plugins:
  - path: ./tools/protoc-gen-custom
    out: ./gen/custom
  - command: [sh, ./tools/protoc-plugin.sh]
    out: ./gen/script
```

The separate `version` field is also unavailable for `path` and `command`.
