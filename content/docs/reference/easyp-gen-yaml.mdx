---

The <code>easyp.gen.yaml</code> file specifies **consumer-side code generation rules**. Residing alongside consuming applications or service projects, it defines which modules to compile, which plugins to invoke, where generated artifacts should be written, and managed options.

<code>generate.modules</code> selects module identities or local paths. Schema version requirements are declared in <code>protobuf.mod</code>; selected commits and hashes are recorded in <code>protobuf.lock</code>.

## Example Configurations

### Project-Level Generator (<code>backend/easyp.gen.yaml</code>)

~~~yaml
version: v1
generate:
  modules: [proto/user, proto/order]
  managed:
    enabled: true
    override:
      - file_option: go_package_prefix
        value: github.com/acme/backend/gen
      - file_option: go_package_prefix
        module: github.com/acme/user
        value: github.com/acme/backend/gen/user
      - file_option: go_package_prefix
        module: github.com/acme/order
        value: github.com/acme/backend/gen/order
plugins:
  - name: go
    out: .
    with_imports: true
    opts: [module=github.com/acme/backend]
  - name: go-grpc
    out: .
    with_imports: true
    opts: [module=github.com/acme/backend, require_unimplemented_servers=false]
~~~

This example assumes the consumer Go module is <code>github.com/acme/backend</code>. The local modules declare <code>github.com/acme/user</code> and <code>github.com/acme/order</code>, exposing <code>v1/user.proto</code> and <code>v1/order.proto</code>; their shared dependency exposes <code>common/v1/common.proto</code>. Outputs go to separate directories <code>gen/user/v1</code>, <code>gen/order/v1</code>, and <code>gen/common/v1</code>. Different Go packages need different output directories; EasyP does not insert an implicit module-name prefix.

### Remote Web Generator (<code>frontend/easyp.gen.yaml</code>)

~~~yaml
version: v1

generate:
  modules:
    - proto/user

plugins:
  - remote: gen.easyp.tech/es
    version: v2.0.0
    out: ./src/gen
    opts:
      target: ts
~~~

## Managed Options (<code>options</code>)

Instead of requiring explicit file-level options (like <code>option go_package = "..."</code>) inside every individual <code>.proto</code> schema file, EasyP's managed <code>options</code> block groups settings logically by target language.

<code>options.go.package_prefix</code> computes <code>go_package</code> from the proto file path without changing the source. The prefix alone changes Go options only: it does not enable Java, C#, PHP, Ruby, Objective-C, or C++ defaults. Full managed mode and field-option transformations require explicit <code>generate.managed.enabled: true</code>. Go disable selectors, including <code>go_package</code>, suppress the prefix.

The existing managed-mode rules remain available under <code>generate.managed</code>. For example, a package-specific override can be written as:

~~~yaml
version: v1
generate:
  managed:
    enabled: true
    override:
      - file_option: go_package_prefix
        package: user.v1
        value: github.com/acme/backend/gen/user
plugins:
  - name: go
    out: ./gen/go
~~~

A repository-root <code>easyp.gen.yaml</code> may provide <code>options.go.package_prefix</code> as a default for nested generator files. Nested <code>generate.managed</code> rules take precedence over that inherited default. A prefix declared in the same generator file has the highest priority. Plugin lists stay local to each generator file.

The v1 generator selects complete modules. <code>generate.packages</code> is reserved and unimplemented: omit it or leave it empty; nonempty values cause an error.

Remote plugins require a <code>version</code> such as <code>v2.0.0</code>. EasyP sends that exact version to the remote generator. For local <code>protoc-gen-&#42;</code> executables and bundled WASM plugins, the executable selected at runtime determines the version; the separate <code>version</code> field is rejected because EasyP cannot verify it.

Each plugin declares exactly one source: <code>name</code>, <code>path</code>, <code>command</code>, or <code>remote</code>. Use <code>path</code> for a specific binary and <code>command</code> for an executable plus arguments. Both run from the directory where <code>easyp generate</code> starts and, like any Protobuf plugin, must read a <code>CodeGeneratorRequest</code> from stdin and write a <code>CodeGeneratorResponse</code> to stdout.

~~~yaml
version: v1
plugins:
  - path: ./tools/protoc-gen-custom
    out: ./gen/custom
  - command: [sh, ./tools/protoc-plugin.sh]
    out: ./gen/script
~~~

The separate <code>version</code> field is also unavailable for <code>path</code> and <code>command</code>.

## Project selection and imports

By default, <code>easyp generate</code> selects the closest config in the current directory or a workspace ancestor. Repeat <code>--project</code> to choose multiple consumers explicitly; <code>--all</code> separately opts into recursive selection. <code>--workspace</code> sets the boundary for module paths and inheritance.

<code>plugins[].with_imports</code> defaults to false. True adds transitive imports to that plugin's files to generate. Import descriptors remain available for linking when false. The <code>--descriptor_set_out</code> and <code>--descriptor_set_out_dir</code> flags are mutually exclusive; <code>--include_imports</code> controls exported contents only, independently of <code>with_imports</code>. See [project selection and descriptor export](/docs/cli/generator).

## Managed-option validation

Both configuration validation and generation reject unknown managed file or field options and values of the wrong type. Boolean options such as <code>java_multiple_files</code> require a YAML boolean, not a quoted string. String options require strings. <code>optimize_for</code> accepts <code>SPEED</code>, <code>CODE_SIZE</code> or <code>LITE_RUNTIME</code>; <code>jstype</code> accepts <code>JS_NORMAL</code>, <code>JS_STRING</code> or <code>JS_NUMBER</code>. Invalid rules cannot silently fall back to managed defaults.

Place a remote version in the separate <code>version</code> field, not after a colon in the final plugin path. A server port in the host is allowed. For example, use <code>remote: localhost:8080/go</code> with <code>version: v1.2.3</code>.
