Файл <code>protobuf.mod</code> располагается в корне proto-модуля. Задуманный как **tool-neutral стандарт**, он не содержит настроек конкретных инструментов (ни флагов линтеров, ни плагинов генерации). Файл сфокусирован исключительно на идентификации модуля, внутренних директориях, объявлениях зависимостей и локальных переопределениях источников.

## Пример спецификации

~~~protobuf
// proto/user/protobuf.mod

module github.com/acme/user

roots (
    proto
)

require (
    github.com/googleapis/googleapis v1.5.0
    github.com/acme/weather v1.2.3
    github.com/acme/gateway/v2 v2.19.0 // indirect
)

// Локальное переопределения для отладки
replace github.com/acme/weather => ../weather-fork
~~~

## Правила поведения

1. **Git-Native идентичность**: Каноническим идентификатором модуля является его Git URL (<code>github.com/acme/weather</code>).
2. **Помодульный скоуп**: Каждый модуль имеет собственный <code>protobuf.mod</code>. MVS работает помодульно (per-module), не навязывая глобальных ограничений версий в монорепозитории.
3. **Локальные замены**: Применяются только директивы главного модуля, включая транзитивные требования; замены в зависимостях игнорируются. Сама замена не добавляет модуль в граф. При наличии <code>replace</code> команды работают с локальным эффективным графом и сохраняют <code>protobuf.lock</code> побайтно; отсутствующий lock не создаётся. <code>mod tidy</code> также не меняет манифест. <code>get</code> и <code>mod update</code> могут менять явные требования, но не добавляют транзитивные зависимости только из форка. <code>mod download</code> устанавливает только нужные незаменённые снимки. Для публикуемого lock удалите замены и выполните <code>mod tidy</code>. Подробнее: [локальные замены](/ru/docs/guides/debugging-replace).

Для нескольких модулей положите <code>protobuf.mod</code> в каталог каждого. Команды <code>mod</code> и <code>get</code> выбирают ближайший манифест в предках в пределах workspace; каждый модуль сохраняет свой <code>protobuf.lock</code>. <code>generate.modules</code> выбирает локальные модули по имени или пути относительно workspace. В потребителе каждый вложенный Git-модуль объявляется отдельно по имени из его манифеста.

Версию можно опустить, например <code>require github.com/acme/contracts/proto/user</code>. Такое требование не добавляет ограничения, если граф уже задаёт SemVer или точный коммит. Только оставшееся неограниченным требование использует прежний коммит lock при <code>tidy</code> либо текущий HEAD без lock; <code>mod update</code> освежает его до HEAD. Явный полный хеш из 40 или 64 hex-символов остаётся точным ограничением.

SemVer-требования выбирают максимум запрошенных минимумов. SemVer и SHA совместимы, только если выбранный тег указывает на этот точный коммит. Разные явные коммиты или выбранный тег на другом коммите вызывают конфликт; порядок версий из SHA, даты или истории коммитов не выводится. Для вложенного модуля в <code>proto/user</code> версия <code>v1.2.3</code> использует тег <code>proto/user/v1.2.3</code>. У каждого модуля своя запись lock и корни.

Локальный <code>replace</code> может указывать на каталог вложенного модуля. Его нативный манифест должен объявлять заменяемое имя; требования замены участвуют в эффективном графе. Относительные пути всегда считаются от главного манифеста, даже на транзитивной глубине; абсолютные используются напрямую. Для исторических breaking-сравнений пути внутри репозитория отображаются в снимок соответствующей ревизии, внешние локальные пути отклоняются. Сохранение lock — явный инвариант EasyP, а не утверждение, что Go никогда не меняет <code>go.sum</code>.

Например, если в <code>repo/foo/protobuf.mod</code> указано <code>roots proto</code>, EasyP читает файлы из физического пути <code>repo/foo/proto</code> внутри репозитория. У файла <code>repo/foo/proto/user/v1/user.proto</code> protobuf import path будет <code>user/v1/user.proto</code>: путь импорта считается относительно вычисленного root, поэтому каталог модуля и сам root в импорте не повторяются. При <code>roots .</code> физический root — <code>repo/foo</code>.

## Идентичность мажорных версий

v0 и v1 используют один путь без суффикса. Для v2 и выше нужен последний компонент <code>/vN</code>, совпадающий с major в SemVer, без ведущих нулей: <code>require github.com/acme/weather/v2 v2.1.0</code>. Суффиксы модуля <code>/v0</code>, <code>/v1</code>, <code>/v01</code> и <code>/v2.0</code> недопустимы. Обычные компоненты <code>/2024</code> и <code>/v2beta</code> не считаются суффиксами. Правило не ограничивает каталоги пакетов и protobuf import paths. Общие с Go функции проверки также распознают особую запись <code>gopkg.in/name.vN</code>.

Проверяются объявленное имя модуля, требования, исходные имена в replace, загруженные нативные метаданные и записи lock. Полный коммит и отсутствие версии не отменяют точного совпадения нативного имени. Абсолютные локальные Git-пути и явные URL поддерживаются: логический host/path проверяется отдельно от учётных данных и порта транспорта. Исходное написание идентификатора сохраняется.

| Идентификатор | Физический каталог с <code>protobuf.mod</code> | Тег примера релиза |
|---|---|---|
| <code>repo</code> | корень репозитория | <code>v1.2.0</code> |
| <code>repo/v2</code> | корень или <code>v2/</code> | <code>v2.0.0</code> |
| <code>repo/sub/v2</code> | <code>sub/</code> или <code>sub/v2/</code> | <code>sub/v2.0.0</code> |

Мажорный суффикс логический и не входит в префикс тега: <code>v2/v2.0.0</code> не является тегом релиза <code>repo/v2</code>. Поддерживаются обычные и аннотированные теги. Манифест в допустимом каталоге должен объявлять точный запрошенный идентификатор; одного совпадения тега недостаточно.

<code>repo</code> и <code>repo/v2</code> могут сосуществовать как разные идентификаторы модулей, записей lock и замен. MVS выбирает максимум запрошенных минимумов для каждого имени отдельно. Различные protobuf import paths задаёт автор: EasyP не переименовывает пакеты и импорты, а совпадение путей импорта остаётся ошибкой. Обновления внутри major, точное согласование SHA/тега, неизменность тегов, сохранение lock при локальных заменах и frozen-проверки сохраняются.

Домодульное исключение <code>+incompatible</code> поддерживается только для v2+ без суффикса пути и без нативного <code>protobuf.mod</code> в выбранной ревизии. EasyP читает исходный Git-тег без этой метки и проверяет метаданные точного скачанного или кешированного коммита до принятия записи lock. При наличии нативного manifest метка не обходит проверку. Обновления старого модуля сохраняют метку; локальные замены остаются неверсионируемым наложением и не записывают свой граф в lock. Миграция не переименовывает источник и не меняет версию молча.

См. [мажорные суффиксы Go](https://go.dev/ref/mod#major-version-suffixes) и [соответствие версий коммитам](https://go.dev/ref/mod#vcs-version).

Как и в Go, локальная замена без опубликованной версии может содержать нативный манифест с тем же именем без суффикса для явного требования <code>+incompatible</code>. Это не подтверждает опубликованную ревизию: локальный граф сохраняет общий lock, а frozen-режим запрещает замены. Загрузка опубликованных версий и установка lock в холодном и прогретом кеше по-прежнему проверяют домодульные метаданные.
