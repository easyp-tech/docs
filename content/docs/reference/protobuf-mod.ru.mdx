Файл <code>protobuf.mod</code> располагается в корне proto-модуля. Задуманный как **tool-neutral стандарт**, он не содержит настроек конкретных инструментов (ни флагов линтеров, ни плагинов генерации). Файл сфокусирован исключительно на идентификации модуля, внутренних директориях, объявлениях зависимостей и локальных переопределениях источников.

## Пример спецификации

~~~protobuf
// proto/user/protobuf.mod

module github.com/acme/user

roots (
    proto
)

require (
    github.com/googleapis/googleapis v1.5.0
    github.com/acme/weather v1.2.3
    github.com/grpc-ecosystem/grpc-gateway v2.19.0 // indirect
)

// Локальное переопределения для отладки
replace github.com/acme/weather => ../weather-fork
~~~

## Правила поведения

1. **Git-Native идентичность**: Каноническим идентификатором модуля является его Git URL (<code>github.com/acme/weather</code>).
2. **Помодульный скоуп**: Каждый модуль имеет собственный <code>protobuf.mod</code>. MVS работает помодульно (per-module), не навязывая глобальных ограничений версий в монорепозитории.
3. **Защита lock-файла**: Локальный <code>replace</code> работает при генерации. <code>easyp get</code>, <code>easyp mod tidy</code> и <code>easyp mod update</code> отклоняют его до удаления, чтобы в воспроизводимый Git lock не попал локальный путь.

Для нескольких модулей положите <code>protobuf.mod</code> в каталог каждого. Команды <code>mod</code> и <code>get</code> выбирают ближайший манифест в предках в пределах workspace; каждый модуль сохраняет свой <code>protobuf.lock</code>. <code>generate.modules</code> выбирает локальные модули по имени или пути относительно workspace. В потребителе каждый вложенный Git-модуль объявляется отдельно по имени из его манифеста.

Версию можно опустить, например <code>require github.com/acme/contracts/proto/user</code>. Такое требование не добавляет ограничения, если граф уже задаёт SemVer или точный коммит. Только оставшееся неограниченным требование использует прежний коммит lock при <code>tidy</code> либо текущий HEAD без lock; <code>mod update</code> освежает его до HEAD. Явный полный хеш из 40 или 64 hex-символов остаётся точным ограничением.

SemVer-требования выбирают максимум запрошенных минимумов. SemVer и SHA совместимы, только если выбранный тег указывает на этот точный коммит. Разные явные коммиты или выбранный тег на другом коммите вызывают конфликт; порядок версий из SHA, даты или истории коммитов не выводится. Для вложенного модуля в <code>proto/user</code> версия <code>v1.2.3</code> использует тег <code>proto/user/v1.2.3</code>. У каждого модуля своя запись lock и корни.

Локальный <code>replace</code> может указывать на вложенный модуль. Относительный путь считается от содержащего его <code>protobuf.mod</code>, абсолютный используется напрямую; каталог потребителя генерации не меняет эту базу. При breaking-сравнении замена внутри репозитория берётся из соответствующей ревизии, а внешняя локальная замена отклоняется.

Например, если в <code>repo/foo/protobuf.mod</code> указано <code>roots proto</code>, EasyP читает файлы из физического пути <code>repo/foo/proto</code> внутри репозитория. У файла <code>repo/foo/proto/user/v1/user.proto</code> protobuf import path будет <code>user/v1/user.proto</code>: путь импорта считается относительно вычисленного root, поэтому каталог модуля и сам root в импорте не повторяются. При <code>roots .</code> физический root — <code>repo/foo</code>.
