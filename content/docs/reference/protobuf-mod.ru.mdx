Файл `protobuf.mod` располагается в корне proto-модуля. Задуманный как **tool-neutral стандарт**, он не содержит настроек конкретных инструментов (ни флагов линтеров, ни плагинов генерации). Файл сфокусирован исключительно на идентификации модуля, внутренних директориях, объявлениях зависимостей и локальных переопределениях источников.

## Пример спецификации

```protobuf
// proto/user/protobuf.mod

module github.com/acme/user

roots (
    proto
)

require (
    github.com/googleapis/googleapis v1.5.0
    github.com/acme/weather v1.2.3
    github.com/grpc-ecosystem/grpc-gateway v2.19.0 // indirect
)

// Локальное переопределения для отладки
replace github.com/acme/weather => ../weather-fork
```

## Правила поведения

1. **Git-Native идентичность**: Каноническим идентификатором модуля является его Git URL (`github.com/acme/weather`).
2. **Помодульный скоуп**: Каждый модуль имеет собственный `protobuf.mod`. MVS работает помодульно (per-module), не навязывая глобальных ограничений версий в монорепозитории.
3. **Защита lock-файла**: Локальный `replace` работает при генерации. `easyp mod tidy` и `easyp mod update` отклоняют его до удаления, чтобы в воспроизводимый Git lock не попал локальный путь.

Если в одном репозитории несколько модулей, разместите `protobuf.mod` в каталоге каждого. Запускайте `easyp mod tidy` из каталога каждого локального модуля: у каждого будет свой `protobuf.lock`. `generate.modules` выбирает локальные модули по пути относительно репозитория или по имени. Потребитель объявляет каждый вложенный Git-модуль отдельным требованием по имени из его манифеста. Например, для `require github.com/acme/contracts/proto/user` не нужны ни тег, ни вручную указанный коммит: `mod tidy` найдёт текущий HEAD репозитория и запишет точный коммит в `protobuf.lock`. Повторный `tidy` сохранит его; `mod update` обновит требование без версии до текущего HEAD. Явно указанный полный хеш коммита из 40 или 64 символов останется закреплённым при обновлении. SemVer-теги также поддерживаются: для вложенного модуля с версией `v1.2.3` тег называется `proto/user/v1.2.3` по [правилу Go для репозиториев с несколькими модулями](https://go.dev/ref/mod#mapping-versions-to-commits). У каждого требуемого модуля своя запись lock и корни исходников. Локальный `replace` может указывать на каталог вложенного модуля.

Например, если в `repo/foo/protobuf.mod` указано `roots proto`, EasyP читает файлы из физического пути `repo/foo/proto` внутри репозитория. У файла `repo/foo/proto/user/v1/user.proto` protobuf import path будет `user/v1/user.proto`: путь импорта считается относительно вычисленного root, поэтому каталог модуля и сам root в импорте не повторяются. При `roots .` физический root — `repo/foo`.
