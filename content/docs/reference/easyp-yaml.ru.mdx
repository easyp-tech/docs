---

Файл <code>easyp.yaml</code> задаёт политики линтинга и совместимости для protobuf-схем. Для каждой секции применяется ближайшее определение в дереве каталогов. Явная загрузка политик через <code>linters.extends</code> и <code>breaking.extends</code> зарезервирована и не реализована: эти поля нужно опустить или оставить пустыми.

## Пример конфигурации

~~~yaml
version: v1
linters:
  default: STANDARD
  enable: [ENUM_VALUE_PREFIX, RPC_REQUEST_RESPONSE_UNIQUE]
  disable: [PACKAGE_VERSION_SUFFIX]
  allow_comment_ignores: true
linters-settings:
  ENUM_ZERO_VALUE_SUFFIX:
    suffix: UNSPECIFIED
  SERVICE_SUFFIX:
    suffix: Service
issues:
  exclude-rules:
    - path: legacy/**/*.proto
      linters: [FIELD_LOWER_SNAKE_CASE]
    - path: generated
breaking:
  baseline: git:main
  categories: [FILE]
  ignore_unstable: true
  ignore: [gen]
~~~

## Каскадирование секций

Секции <code>linters</code>, <code>linters-settings</code>, <code>issues</code> и <code>breaking</code> берутся целиком из ближайшего определяющего файла без частичного слияния. Вложенная <code>issues: &#123;&#125;</code> очищает унаследованные исключения. Унаследованный путь исключения остаётся относительно файла, где определена секция <code>issues</code>, даже если запуск или <code>--root</code> указывает глубже.

При поиске политики команды идут вверх в пределах workspace. Если политики выше нет, допустима одна однозначная внешняя политика в потомках; несколько независимых политик требуют явного <code>--cfg</code>. Явный <code>--cfg</code> имеет приоритет, а явный <code>--root</code> задаёт начальную точку поиска по умолчанию.

## Выбор правил и исключения

Повторные имена правил или групп не добавляют проверок; отключение приоритетнее включения. Неизвестные имена в enable, disable и исключениях — ошибки, даже если имя есть в противоположном списке. Зарезервированное <code>PACKAGE_NO_IMPORT_CYCLE</code> не реализовано и выбирать его нельзя.

Пути <code>issues.exclude-rules[].path</code> используют разделитель <code>/</code> и привязаны к каталогу файла, предоставившего эффективную секцию <code>issues</code>:

| Шаблон | Совпадение |
| --- | --- |
| <code>generated</code> | Весь каталог и его поддерево |
| <code>api/file.proto</code> | Этот файл |
| <code>api/&#42;.proto</code> | Файлы непосредственно в api |
| <code>api/?.proto</code> | Имя из одного символа перед .proto |
| <code>api/[a-c].proto</code> | a.proto, b.proto или c.proto |
| <code>api/&#42;&#42;/file.proto</code> | Ноль или больше промежуточных каталогов |

<code>&#42;&#42;</code> должен занимать целый сегмент. Абсолютные пути, обратные слеши, переходы <code>..</code> и некорректные шаблоны отклоняются. Путь без шаблонов с окончанием <code>.proto</code> совпадает только с файлом; остальные буквальные пути охватывают поддерево. Эти правила относятся только к исключениям issues, а не ко всем путям конфигурации.

Без <code>path</code> правило действует на все файлы эффективной секции issues. <code>linters</code> может содержать реализованные правила или группы; пустой либо отсутствующий список исключает файл из линтинга целиком. Полностью пустое правило <code>&#123;&#125;</code> сохраняет значение явного исключения всех файлов. В примере исключается всё поддерево <code>generated</code>, а в <code>legacy</code> подавляется только указанное правило.

## Подавление комментариями

<code>linters.allow_comment_ignores</code> по умолчанию равен true для каждой эффективной политики. False отключает подавление через комментарии. Маркеры <code>easyp:disable</code>/<code>easyp:enable</code> задают аннотации или ограниченные регионы; старые <code>nolint:RULE</code> и <code>buf:lint:ignore RULE</code> остаются аннотациями. Неизвестные имена, пустые директивы и непарные enable остаются ошибками даже при отключённом подавлении. Примеры и области действия — в [руководстве линтера](/ru/docs/cli/linter).

## Проверка совместимости

Явный <code>--against</code> имеет приоритет над <code>breaking.baseline</code>; без обоих используется <code>master</code>. Это верно и для явного <code>--against master</code>. Пустой явный флаг вызывает ошибку, а отсутствующая Git-база не заменяется конфигурационной.

База может указывать на локальную ветку, лёгкий или аннотированный тег, полный SHA коммита или другую разрешимую локально Git-ревизию, например <code>HEAD</code>. Нужные ссылки и объекты должны уже присутствовать в checkout. Короткое имя ветки приоритетнее одноимённого тега; для явного выбора тега используйте <code>refs/tags/v1.2.0</code>. В YAML задавайте <code>git:refs/tags/v1.2.0</code>, а в CLI — <code>--against refs/tags/v1.2.0</code> без префикса <code>git:</code> или <code>git-ref=</code>.

Пути <code>breaking.ignore</code> отсчитываются от файла, задающего эффективную секцию <code>breaking</code>, а не от корня Git или <code>--root</code>. Например, <code>ignore: [generated]</code> в <code>api/easyp.yaml</code> исключает <code>api/generated</code>, в том числе при наследовании этой секции. Допустимы непустые локальные относительные пути; абсолютные пути и выход за каталог политики или репозиторий отклоняются.

Для каждого выбранного модуля текущая и базовая ревизии используют собственные корни, манифесты и lock. База читается из изолированного Git-снимка; рабочее дерево, манифест и lock пользователя не изменяются. Политики берутся из текущей конфигурации; каждая может задавать свою базу. Подробности и ограничения локальных замен — в [руководстве breaking](/ru/docs/cli/breaking-changes).

Единственная поддерживаемая дополнительная категория — <code>FILE</code>, проверяющая перемещения объявлений между файлами. Она не выключает существующие проверки. Категории <code>PACKAGE</code>, <code>WIRE</code>, <code>WIRE_JSON</code> и другие пока не реализованы; включать их нельзя. <code>linters.extends</code> и <code>breaking.extends</code> также не загружают локальные или удалённые общие политики: непустые значения отклоняются.

## Нестабильные пакеты

<code>breaking.ignore_unstable</code> по умолчанию равен false. При true фильтруется последний компонент имени protobuf-пакета на обеих сторонах сравнения, включая пакеты зависимостей. Поддерживаются формы <code>vNtest...</code>, <code>vNalpha</code>, <code>vNbeta</code>, <code>vNpMalpha</code> и <code>vNpMbeta</code>. После alpha/beta допустим положительный номер; N, M и этот номер начинаются с 1–9 и продолжаются цифрами. После test допустим любой суффикс, включая пустой.

Например, <code>acme.v1testFeature</code>, <code>acme.v2alpha3</code> и <code>acme.v2p3beta</code> пропускаются. <code>acme.v1</code>, <code>acme.v0alpha1</code>, <code>acme.v1beta0</code> и <code>acme.v1beta1.service</code> не совпадают. Стабильные пакеты по-прежнему проверяются, включая их ссылки на нестабильные типы. Фильтр не позволяет оставить некорректные исходники: чтение и разрешение импортов происходят до фильтрации.
