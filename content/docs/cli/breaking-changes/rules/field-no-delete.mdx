---
title: "Field No Delete"
description: "Checks that no message or extension fields are deleted in source-compatibility profiles."
---

- **Rule ID:** `FIELD_NO_DELETE`
- **Profiles:** `FILE`, `PACKAGE`

This rule checks that no fields are deleted from a message. Deleting a field removes generated struct fields and accessor methods, breaking compilation for consumers.

<Callout type="info">
Adding `reserved` for a deleted field number or name does **not** satisfy `FIELD_NO_DELETE` in `FILE` or `PACKAGE` profiles, because generated source accessors are still removed. Reserving deleted field numbers (and names for JSON) only satisfies [`FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED`](/docs/cli/breaking-changes/rules/field-no-delete-unless-number-reserved) (`WIRE`, `WIRE_JSON`) and [`FIELD_NO_DELETE_UNLESS_NAME_RESERVED`](/docs/cli/breaking-changes/rules/field-no-delete-unless-name-reserved) (`WIRE_JSON`).
</Callout>

## Examples

### Bad

**Before:**

```proto
syntax = "proto3";

package myapi.v1;

message User {
  string name = 1;
  string email = 2;
  int32 age = 3;
  string phone = 4;
}
```

**After:**

```proto
syntax = "proto3";

package myapi.v1;

message User {
  reserved 4;
  reserved "phone";

  string name = 1;
  string email = 2;
  int32 age = 3;
}
```

**Error:**

```text
user.proto:9:3: Field "phone" (4) on "myapi.v1.User" was deleted. (FIELD_NO_DELETE)
```

### Good

Keep the field and mark it deprecated instead of deleting it in `FILE`/`PACKAGE` profiles:

```proto
syntax = "proto3";

package myapi.v1;

message User {
  string name = 1;
  string email = 2;
  int32 age = 3;
  string phone = 4 [deprecated = true];
}
```

## Migration Strategy

1. Mark the field with `[deprecated = true]` and stop writing to it in application code.
2. If your policy uses `WIRE` or `WIRE_JSON`, delete the field only while permanently reserving its number (and name for `WIRE_JSON`).
3. If your policy uses `FILE` or `PACKAGE`, keep the deprecated field until the next major package version (for example, `myapi.v2`).
