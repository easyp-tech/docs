The v1 pilot separates module dependencies, generation, and lint and breaking policies:

| File | Purpose |
|------|---------|
| [<code>protobuf.mod</code>](/docs/reference/protobuf-mod) | Module identity, source roots, requirements, and local replacements |
| [<code>protobuf.lock</code>](/docs/reference/protobuf-lock) | Resolved Git commits and content hashes; generated by <code>easyp mod tidy</code> |
| [<code>easyp.gen.yaml</code>](/docs/reference/easyp-gen-yaml) | Modules to generate, plugins, outputs, and managed options |
| [<code>easyp.yaml</code>](/docs/reference/easyp-yaml) | Lint and breaking policies |

The CLI commands use the v1 files directly. They do not fall back to the older EasyP generation, lint, breaking, or module-management configuration. A Git dependency can still use older EasyP or Buf configuration: the dependency reader extracts its requirements and proto roots for import resolution.

For guided v0 migration, run <code>easyp migrate</code> in a terminal. Explicit <code>--interactive</code> starts the wizard with supplied values; <code>--interactive=false</code> disables it. Supplying <code>--module</code> without requesting the wizard preserves the original preview. See [v0 migration](/docs/migration/easyp-v0).

## Typical workflow

~~~bash
easyp init --module github.com/acme/contracts
easyp mod tidy
easyp mod download
easyp generate
easyp lint --path proto
easyp breaking --path proto --against main
~~~

Without replacements, <code>mod tidy</code> writes the lock, <code>mod download</code> installs pinned commits, and <code>mod update</code> refreshes requirements within their current major versions and updates the lock. With <code>replace</code>, commands use a local effective graph and preserve <code>protobuf.lock</code> byte-for-byte; a missing lock is not created. <code>mod tidy</code> also leaves the manifest unchanged. <code>get</code> and <code>mod update</code> may edit explicit requirements without adding fork-only transitives. <code>mod download</code> installs only needed unreplaced snapshots. Remove replacements and run <code>mod tidy</code> to produce a publishable lock. See [local replacements](/docs/guides/debugging-replace).

## Explicit frozen mode

Use <code>--frozen</code> for builds that must use the committed dependency graph. It defaults to false and is never inferred from <code>CI=true</code>. Every selected native module whose dependency graph is used needs both <code>protobuf.mod</code> and <code>protobuf.lock</code>, including an empty lock when there are no dependencies. An explicit workspace-relative <code>generate.modules</code> path uses the selected module's manifest and lock, so a directory containing only <code>easyp.gen.yaml</code> needs no separate pair. Dependency identity selectors still require the consumer manifest and lock. The manifest-free source fallback described below applies only without frozen mode.

~~~bash
easyp --frozen generate
easyp lint --frozen --path proto
easyp breaking --frozen --against main
easyp mod --frozen download
easyp mod vendor --frozen
~~~

The flag is accepted globally before the command; locally on <code>generate</code>, <code>lint</code>, <code>breaking</code>, <code>ls-files</code>, <code>get</code>, <code>init</code>, and <code>migrate</code>; and on <code>mod</code> or any of its four subcommands. A true value at any parent or command level enables it. A child <code>--frozen=false</code> cannot cancel a parent's true value.

Frozen rejects every root <code>replace</code>, even unused entries, before accessing replacement paths or fetching dependencies. It checks direct and transitive requirements against the lock and verifies cached content. It never resolves versions, looks up dependency HEAD/tags, or writes either manifest or lock. Missing or stale locks cause an error. Exact locked commits may still be fetched into the cache: frozen is not offline.

<code>mod tidy</code>, <code>get</code>, <code>mod update</code>, <code>init</code>, and <code>migrate</code> refuse frozen execution; migration preview and interactive mode are also refused. Prepare the files outside frozen mode. Generation checks every selected graph before any plugin runs. Lint keeps effective policy scoping; breaking uses the baseline revision's own manifest and lock. Local-only <code>ls-files --include-imports=false</code> still validates the frozen graph. See the [package manager](/docs/cli/package-manager#frozen-builds) for the full dependency contract.

## Command flags

| Command | Relevant flags |
|---------|----------------|
| <code>generate</code> | <code>--project</code> (repeatable), <code>--all</code>, <code>--workspace</code>, <code>--descriptor_set_out</code>, <code>--descriptor_set_out_dir</code>, <code>--include_imports</code> |
| <code>lint</code> | <code>--path</code> (<code>-p</code>), <code>--root</code> (<code>-r</code>) |
| <code>breaking</code> | <code>--path</code> (<code>-p</code>), <code>--root</code> (<code>-r</code>), <code>--against</code> |
| <code>init</code> | <code>--dir</code> (<code>-d</code>), <code>--module</code> |
| <code>validate-config</code> | <code>--config</code> (alias of <code>--cfg</code>), <code>--format</code> |
| <code>mod download/tidy/vendor/update</code> | <code>--frozen</code> |
| <code>ls-files</code> | <code>--include-imports</code> (default <code>true</code>), <code>--format</code> (<code>json</code> or <code>text</code>) |
| <code>schema-gen</code> | <code>--out-dir</code> (default <code>schemas</code>) |

The global flags are <code>--cfg</code> (alias <code>--config</code>, default <code>easyp.yaml</code>), <code>--debug</code> (<code>-d</code>), <code>--format</code> (<code>-f</code>, <code>text</code> or <code>json</code>), and <code>--frozen</code>. <code>EASYP_CFG</code>, <code>EASYP_DEBUG</code>, and <code>EASYP_FORMAT</code> set their respective defaults. The module cache uses <code>EASYPPATH</code> or <code>$HOME/.easyp</code>.

By default, <code>generate</code> selects the closest <code>easyp.gen.yaml</code> in the current directory or a workspace ancestor. Repeat <code>--project</code> for multiple explicit consumers. <code>--all</code> separately opts into recursive selection below the invocation directory and is mutually exclusive with <code>--project</code>. <code>--workspace</code> sets the boundary for module paths and inheritance; by default this is the nearest Git repository or enclosing EasyP files. Modules and roots come from <code>protobuf.mod</code>; <code>generate.packages</code> is reserved and rejects nonempty values. The <code>generate --path</code> and <code>generate --root</code> flags are unavailable.

<code>--descriptor_set_out</code> merges compatible graphs into one file; <code>--descriptor_set_out_dir</code> produces an independent file per project/module pair. The flags are mutually exclusive and destinations are invocation-relative. <code>--include_imports</code> defaults to false and affects exports only. <code>plugins[].with_imports</code> also defaults to false but separately enables imported code generation for an individual plugin. <code>options.go.package_prefix</code> changes Go only; full managed mode requires explicit <code>generate.managed.enabled: true</code>.

<code>lint</code> and <code>breaking</code> read the v1 <code>easyp.yaml</code>. They use the nearest module's declared roots and locked or local dependency roots for imports. A policy may exist without a <code>protobuf.mod</code>; in that case the commands use the scanned files and built-in imports.

<code>generate</code> and <code>ls-files</code> also work without <code>protobuf.mod</code> when there are no module dependencies: the current project directory is treated as the source root.

EasyP expands environment variables in <code>easyp.yaml</code> and <code>easyp.gen.yaml</code> before parsing or validation. <code>$&#123;NAME&#125;</code> uses the variable value, <code>$&#123;NAME:-default&#125;</code> supplies a fallback, and <code>$$&#123;NAME&#125;</code> leaves a literal <code>$&#123;NAME&#125;</code>. An unset variable without a fallback becomes an empty string. YAML comments are ignored during expansion. <code>protobuf.mod</code> and <code>protobuf.lock</code> do not use this substitution.

For <code>breaking</code>, explicit <code>--against</code> overrides <code>breaking.baseline</code>, followed by the default <code>master</code>. Each revision uses its own roots, manifests, and locks; the baseline comes from an isolated Git snapshot. Policies come from current configuration and sections are inherited as a whole. The additional category <code>FILE</code> is supported; package-related and other categories are reserved and rejected. <code>breaking.ignore_unstable</code> defaults to false; its exact unstable suffix forms are in the [reference](/docs/reference/easyp-yaml#unstable-packages).

<code>issues.exclude-rules.path</code> is relative to the file supplying the issues section and supports <code>&#42;</code>, <code>?</code>, <code>[]</code>, and complete <code>&#42;&#42;</code> segments. Literal directories cover their subtree. An empty rule <code>&#123;&#125;</code> explicitly ignores all files. <code>linters.allow_comment_ignores</code> defaults to true per policy. <code>linters.extends</code> and <code>breaking.extends</code> load section-scoped bases from bounded local paths or existing locked modules; see [shared policies](/docs/guides/organization-lint-style).

<code>validate-config</code> recursively checks every <code>easyp.yaml</code>, <code>easyp.gen.yaml</code>, <code>protobuf.mod</code>, and <code>protobuf.lock</code> below the current directory. Pass <code>--cfg &lt;file&gt;</code> to check one file or <code>--cfg &lt;directory&gt;</code> to scan another directory. JSON errors identify the file; YAML structure errors also include line and column. Invalid lock versions, incomplete entries, and malformed hashes are reported as validation errors.

~~~bash
easyp validate-config
easyp validate-config --cfg ./services --format json
easyp validate-config --cfg ./services/api/easyp.gen.yaml
~~~

<code>mod vendor</code> verifies the locked Git dependencies and copies their <code>.proto</code> files into <code>easyp_vendor</code> using their import paths. It replaces a previous vendor tree only after all files have been copied successfully. Duplicate import paths are errors. With local <code>replace</code> directives it copies the effective local and verified remote graph without changing the published lock.

<code>ls-files</code> lists local <code>.proto</code> files from <code>protobuf.mod</code> roots. By default it also includes reachable imports from dependencies and bundled well-known protos, resolving dependencies through the v1 lock or local replacements. Use <code>--include-imports=false</code> to list only local files; outside frozen mode this skips dependency resolution. JSON output contains <code>files</code>, <code>roots</code>, and any import <code>errors</code>.

<code>schema-gen --out-dir schemas</code> writes separate JSON Schemas for <code>easyp.yaml</code>, <code>easyp.gen.yaml</code>, and <code>protobuf.lock</code>, each with a <code>-v1.schema.json</code> filename and an unversioned alias. <code>protobuf.mod</code> is a text manifest, so validate it with <code>validate-config</code> instead. CLI validation also checks semantic rules beyond the JSON Schemas.

The exported <code>github.com/easyp-tech/easyp/mcp/easypconfig</code> package registers <code>easyp_config_describe</code> with an MCP server through <code>easypconfig.RegisterTool(server)</code>. The tool describes the two editable YAML files and reads the same JSON Schemas as <code>schema-gen</code>. It does not describe <code>protobuf.mod</code> or <code>protobuf.lock</code>.

## Minimal files

~~~text
module github.com/acme/contracts
roots proto
require github.com/acme/shared v1.2.0
~~~

~~~yaml
# easyp.gen.yaml
version: v1
generate:
  modules: [github.com/acme/contracts]
plugins:
  - name: go
    out: ./gen/go
~~~

~~~yaml
# easyp.yaml
version: v1
linters:
  default: STANDARD
breaking:
  baseline: git:main
~~~

For the exact fields and current limits, use the linked reference pages above.

## Errors and noninteractive use

<code>ls-files</code> prints its complete JSON or text result, then exits with a nonzero status when import traversal reported an error. A JSON <code>errors</code> array is not a successful build. <code>--include-imports=false</code> deliberately lists only local files; it is not an import-integrity check.

<code>init</code> never opens a hidden controlling terminal behind redirected input or output. Supply <code>--module</code> when no identity can be read locally. An origin-based identity comes from the declared Git remote URL, before transport-only <code>insteadOf</code> rewriting. Overwriting a different existing configuration requires terminal confirmation; piped answers are not accepted.

Policy syntax and supported setting names are checked by execution as well as <code>validate-config</code>. A nonempty breaking baseline must have the <code>git:</code> prefix. Lint groups checked files by effective policy and module while preserving per-file exclusions and diagnostic order.
