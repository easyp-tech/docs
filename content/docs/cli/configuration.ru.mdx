В пилотной версии v1 зависимости, генерация и правила проверки находятся в разных файлах:

| Файл | Назначение |
|------|------------|
| [`protobuf.mod`](/ru/docs/reference/protobuf-mod) | Имя модуля, корни исходников, зависимости и локальные замены |
| [`protobuf.lock`](/ru/docs/reference/protobuf-lock) | Зафиксированные Git-коммиты и хеши содержимого; создаётся командой `easyp mod tidy` |
| [`easyp.gen.yaml`](/ru/docs/reference/easyp-gen-yaml) | Модули для генерации, плагины, выходные каталоги и managed mode |
| [`easyp.yaml`](/ru/docs/reference/easyp-yaml) | Правила линтинга и проверки совместимости |

Команды CLI читают формат v1 напрямую и не переходят на старую логику генерации, линтинга, проверки совместимости или управления модулями. Зависимость в Git при этом может использовать старый формат EasyP или Buf: адаптер извлекает её требования и корни `.proto` для разрешения импортов.

## Обычный порядок работы

```bash
easyp init --module github.com/acme/contracts
easyp mod tidy
easyp mod download
easyp generate
easyp lint --path proto
easyp breaking --path proto --against main
```

`mod tidy` разрешает зависимости и записывает `protobuf.lock`. `mod download` скачивает только зафиксированные коммиты. `mod update` обновляет версии в пределах текущей мажорной версии и пересоздаёт lock. Локальные `replace` работают при генерации и линтинге; перед `mod tidy` или `mod update` их нужно убрать, чтобы получить воспроизводимый lock.

## Флаги команд

| Команда | Основные флаги |
|---------|----------------|
| `generate` | `--project`, `--descriptor_set_out`, `--include_imports` |
| `lint` | `--path` (`-p`), `--root` (`-r`) |
| `breaking` | `--path` (`-p`), `--root` (`-r`), `--against` |
| `init` | `--dir` (`-d`), `--module` |
| `validate-config` | `--config` (псевдоним `--cfg`), `--format` |
| `mod vendor` | Нет собственных флагов |
| `ls-files` | `--include-imports` (по умолчанию `true`), `--format` (`json` или `text`) |
| `schema-gen` | `--out-dir` (по умолчанию `schemas`) |

Общие флаги: `--cfg` (псевдоним `--config`, по умолчанию `easyp.yaml`), `--debug` (`-d`) и `--format` (`-f`, `text` или `json`). Переменные `EASYP_CFG`, `EASYP_DEBUG` и `EASYP_FORMAT` задают значения по умолчанию. Кеш модулей находится в `EASYPPATH` или `$HOME/.easyp`.

`generate` ищет `easyp.gen.yaml` внутри текущего каталога. Флаг `--project` выбирает один проект-потребитель. Список модулей и корни исходников берутся из `protobuf.mod`. Поле `generate.packages` зарезервировано: непустое значение пока вызывает ошибку. Старые флаги `generate --path` и `generate --root` удалены.

`lint` и `breaking` читают `easyp.yaml` версии v1. Для импортов они используют корни ближайшего модуля и его зафиксированных или локальных зависимостей. Политика может существовать без `protobuf.mod`; тогда используются проверяемые файлы и встроенные импорты.

`generate` и `ls-files` тоже работают без `protobuf.mod`, если у проекта нет модульных зависимостей: текущий каталог проекта считается корнем исходников.

Перед разбором и проверкой `easyp.yaml` и `easyp.gen.yaml` EasyP подставляет переменные окружения. `${NAME}` берёт значение переменной, `${NAME:-default}` задаёт запасное значение, а `$${NAME}` оставляет буквальную строку `${NAME}`. Отсутствующая переменная без запасного значения превращается в пустую строку. Подстановки в комментариях YAML игнорируются. В `protobuf.mod` и `protobuf.lock` такой подстановки нет.

`breaking` применяет ближайшую секцию `breaking` к каждому файлу с ошибкой. Если вложенные политики выбирают разные Git-базы, команда сравнивает файлы с каждой базой и относит ошибку только к выбравшей её политике.

`validate-config` рекурсивно проверяет все `easyp.yaml`, `easyp.gen.yaml`, `protobuf.mod` и `protobuf.lock` внутри текущего каталога. Передайте `--cfg <файл>`, чтобы проверить один файл, или `--cfg <каталог>`, чтобы проверить другой каталог. В JSON-ошибках указан файл, а для ошибок структуры YAML — строка и столбец. Некорректная версия lock-файла, неполные записи и неверные хеши выдаются как ошибки проверки.

```bash
easyp validate-config
easyp validate-config --cfg ./services --format json
easyp validate-config --cfg ./services/api/easyp.gen.yaml
```

`mod vendor` проверяет зафиксированные Git-зависимости и копирует их `.proto` в `easyp_vendor` по import path. Старый каталог заменяется только после успешного копирования всех файлов. Совпадающие import path вызывают ошибку. Сначала выполните `mod tidy`; локальные `replace` нельзя вендорить.

`ls-files` показывает локальные `.proto` из корней `protobuf.mod`. По умолчанию команда также включает достижимые импорты из зависимостей и встроенных well-known proto, разрешая зависимости через v1 lock или локальные замены. `--include-imports=false` показывает только локальные файлы без разрешения зависимостей. В JSON есть поля `files`, `roots` и, при проблемах с импортами, `errors`.

`schema-gen --out-dir schemas` создаёт отдельные JSON Schema для `easyp.yaml`, `easyp.gen.yaml` и `protobuf.lock`: файлы с суффиксом `-v1.schema.json` и псевдонимы без версии. `protobuf.mod` — текстовый манифест; проверяйте его командой `validate-config`. CLI также проверяет семантические правила, не выраженные в JSON Schema.

Экспортируемый пакет `github.com/easyp-tech/easyp/mcp/easypconfig` регистрирует инструмент `easyp_config_describe` в MCP-сервере через `easypconfig.RegisterTool(server)`. Инструмент описывает два редактируемых YAML-файла и использует те же JSON Schema, что и `schema-gen`. Он не описывает `protobuf.mod` и `protobuf.lock`.

## Минимальный пример

```text
module github.com/acme/contracts
roots proto
require github.com/acme/shared v1.2.0
```

```yaml
# easyp.gen.yaml
version: v1
generate:
  modules: [github.com/acme/contracts]
plugins:
  - name: go
    out: ./gen/go
```

```yaml
# easyp.yaml
version: v1
linters:
  default: STANDARD
breaking:
  baseline: git:main
```

Точные поля и текущие ограничения описаны в справочниках по ссылкам выше.
