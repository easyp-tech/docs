В пилотной версии v1 зависимости, генерация и правила проверки находятся в разных файлах:

| Файл | Назначение |
|------|------------|
| [<code>protobuf.mod</code>](/ru/docs/reference/protobuf-mod) | Имя модуля, корни исходников, зависимости и локальные замены |
| [<code>protobuf.lock</code>](/ru/docs/reference/protobuf-lock) | Зафиксированные Git-коммиты и хеши содержимого; создаётся командой <code>easyp mod tidy</code> |
| [<code>easyp.gen.yaml</code>](/ru/docs/reference/easyp-gen-yaml) | Модули для генерации, плагины, выходные каталоги и managed mode |
| [<code>easyp.yaml</code>](/ru/docs/reference/easyp-yaml) | Правила линтинга и проверки совместимости |

Команды CLI читают формат v1 напрямую и не переходят на старую логику генерации, линтинга, проверки совместимости или управления модулями. Зависимость в Git при этом может использовать старый формат EasyP или Buf: адаптер извлекает её требования и корни <code>.proto</code> для разрешения импортов.

Для интерактивного перехода с v0 выполните <code>easyp migrate</code> в терминале. Явный <code>--interactive</code> включает мастер с уже заданными параметрами, <code>--interactive=false</code> отключает его. Вызов с <code>--module</code> без включения мастера сохраняет прежний предварительный просмотр. См. [миграцию v0](/ru/docs/migration/easyp-v0).

## Обычный порядок работы

~~~bash
easyp init --module github.com/acme/contracts
easyp mod tidy
easyp mod download
easyp generate
easyp lint --path proto
easyp breaking --path proto --against main
~~~

Без замен <code>mod tidy</code> записывает lock, <code>mod download</code> устанавливает зафиксированные коммиты, а <code>mod update</code> обновляет требования в пределах текущей мажорной версии и lock. При наличии <code>replace</code> команды работают с локальным эффективным графом и сохраняют <code>protobuf.lock</code> побайтно; отсутствующий lock не создаётся. <code>mod tidy</code> также не меняет манифест. <code>get</code> и <code>mod update</code> могут менять явные требования, но не добавляют транзитивные зависимости только из форка. <code>mod download</code> устанавливает только нужные незаменённые снимки. Для публикуемого lock удалите замены и выполните <code>mod tidy</code>. Подробнее: [локальные замены](/ru/docs/guides/debugging-replace).

## Явный режим frozen

Используйте <code>--frozen</code>, когда сборка должна опираться на сохранённый граф зависимостей. По умолчанию флаг выключен; <code>CI=true</code> его не включает. Каждому выбранному native-модулю, чей граф зависимостей используется, нужны <code>protobuf.mod</code> и <code>protobuf.lock</code>, в том числе пустой lock при отсутствии зависимостей. Явный путь от workspace в <code>generate.modules</code> использует манифест и lock выбранного модуля; каталогу только с <code>easyp.gen.yaml</code> отдельная пара не нужна. Выбор зависимости по идентификатору по-прежнему требует манифест и lock потребителя. Описанный ниже запуск исходников без манифеста доступен только без frozen.

~~~bash
easyp --frozen generate
easyp lint --frozen --path proto
easyp breaking --frozen --against main
easyp mod --frozen download
easyp mod vendor --frozen
~~~

Флаг принимается глобально перед командой; локально у <code>generate</code>, <code>lint</code>, <code>breaking</code>, <code>ls-files</code>, <code>get</code>, <code>init</code> и <code>migrate</code>; у родительской команды <code>mod</code> и каждой из четырёх её подкоманд. Значение true на любом уровне включает режим. Дочерний <code>--frozen=false</code> не отменяет true у родителя.

Frozen отклоняет все корневые <code>replace</code>, даже неиспользуемые, до обращения к путям замен или скачивания зависимостей. Проверяются прямые и транзитивные требования относительно lock и содержимое кеша. Режим не разрешает версии заново, не ищет HEAD/теги зависимостей и не записывает манифест или lock. Отсутствующий или устаревший lock вызывает ошибку. Точные коммиты из lock могут загружаться в кеш: frozen не означает автономную работу без сети.

<code>mod tidy</code>, <code>get</code>, <code>mod update</code>, <code>init</code> и <code>migrate</code> отклоняют запуск в frozen; предварительный просмотр и интерактивная миграция тоже запрещены. Подготовьте файлы вне frozen. Генерация проверяет все выбранные графы до запуска любого плагина. Lint сохраняет действующую область политик; breaking использует собственные манифест и lock базовой ревизии. Даже <code>ls-files --include-imports=false</code> проверяет frozen-граф. Подробнее — в [менеджере пакетов](/ru/docs/cli/package-manager).

## Флаги команд

| Команда | Основные флаги |
|---------|----------------|
| <code>generate</code> | <code>--project</code> (повторяемый), <code>--all</code>, <code>--workspace</code>, <code>--descriptor_set_out</code>, <code>--descriptor_set_out_dir</code>, <code>--include_imports</code> |
| <code>lint</code> | <code>--path</code> (<code>-p</code>), <code>--root</code> (<code>-r</code>) |
| <code>breaking</code> | <code>--path</code> (<code>-p</code>), <code>--root</code> (<code>-r</code>), <code>--against</code> |
| <code>init</code> | <code>--dir</code> (<code>-d</code>), <code>--module</code> |
| <code>validate-config</code> | <code>--config</code> (псевдоним <code>--cfg</code>), <code>--format</code> |
| <code>mod download/tidy/vendor/update</code> | <code>--frozen</code> |
| <code>ls-files</code> | <code>--include-imports</code> (по умолчанию <code>true</code>), <code>--format</code> (<code>json</code> или <code>text</code>) |
| <code>schema-gen</code> | <code>--out-dir</code> (по умолчанию <code>schemas</code>) |

Общие флаги: <code>--cfg</code> (псевдоним <code>--config</code>, по умолчанию <code>easyp.yaml</code>), <code>--debug</code> (<code>-d</code>), <code>--format</code> (<code>-f</code>, <code>text</code> или <code>json</code>) и <code>--frozen</code>. Переменные <code>EASYP_CFG</code>, <code>EASYP_DEBUG</code> и <code>EASYP_FORMAT</code> задают значения по умолчанию. Кеш модулей находится в <code>EASYPPATH</code> или <code>$HOME/.easyp</code>.

По умолчанию <code>generate</code> выбирает ближайший <code>easyp.gen.yaml</code> в текущем или родительском каталоге workspace. <code>--project</code> можно повторять для нескольких явных потребителей. <code>--all</code> отдельно включает рекурсивный выбор внутри каталога запуска и несовместим с <code>--project</code>. <code>--workspace</code> задаёт границу для путей модулей и наследования; по умолчанию используется ближайший Git-репозиторий или охватывающие файлы EasyP. Модули и корни исходников берутся из <code>protobuf.mod</code>; <code>generate.packages</code> выбирает точные имена protobuf-пакетов среди выбранных модулей. Флагов <code>generate --path</code> и <code>generate --root</code> нет.

<code>--descriptor_set_out</code> объединяет совместимые графы в один файл; <code>--descriptor_set_out_dir</code> создаёт независимый файл для каждой пары проект/модуль. Флаги взаимоисключающие, пути считаются от каталога запуска. <code>--include_imports</code> по умолчанию равен false и влияет только на экспорт. <code>plugins[].with_imports</code> также по умолчанию равен false, но отдельно включает генерацию импортов для конкретного плагина. <code>options.go.package_prefix</code> меняет только Go; полный managed mode требует явного <code>generate.managed.enabled: true</code>.

<code>lint</code> и <code>breaking</code> читают <code>easyp.yaml</code> версии v1. Для импортов они используют корни ближайшего модуля и его зафиксированных или локальных зависимостей. Политика может существовать без <code>protobuf.mod</code>; тогда используются проверяемые файлы и встроенные импорты.

<code>generate</code> и <code>ls-files</code> тоже работают без <code>protobuf.mod</code>, если у проекта нет модульных зависимостей: текущий каталог проекта считается корнем исходников.

Перед разбором и проверкой <code>easyp.yaml</code> и <code>easyp.gen.yaml</code> EasyP подставляет переменные окружения. <code>$&#123;NAME&#125;</code> берёт значение переменной, <code>$&#123;NAME:-default&#125;</code> задаёт запасное значение, а <code>$$&#123;NAME&#125;</code> оставляет буквальную строку <code>$&#123;NAME&#125;</code>. Отсутствующая переменная без запасного значения превращается в пустую строку. Подстановки в комментариях YAML игнорируются. В <code>protobuf.mod</code> и <code>protobuf.lock</code> такой подстановки нет.

В <code>breaking</code> явный <code>--against</code> перекрывает <code>breaking.baseline</code>, затем применяется значение по умолчанию <code>master</code>. Каждая ревизия использует собственные корни, манифесты и lock; база читается из изолированного Git-снимка. Политики берутся из текущей конфигурации, секции наследуются целиком. Поддерживается дополнительная категория <code>FILE</code>; пакетные и другие категории зарезервированы и не принимаются. <code>breaking.ignore_unstable</code> по умолчанию равен false; точные формы нестабильных суффиксов описаны в [справочнике](/ru/docs/reference/easyp-yaml#нестабильные-пакеты).

Пути <code>issues.exclude-rules.path</code> считаются от файла, предоставляющего секцию issues, и поддерживают <code>&#42;</code>, <code>?</code>, <code>[]</code> и полные сегменты <code>&#42;&#42;</code>. Буквальный каталог охватывает поддерево. Пустое правило <code>&#123;&#125;</code> явно исключает все файлы. <code>linters.allow_comment_ignores</code> по умолчанию равен true для каждой политики. <code>linters.extends</code> и <code>breaking.extends</code> подключают базы отдельных секций из локальных путей или существующих закреплённых модулей; см. [общие политики](/ru/docs/guides/organization-lint-style).

<code>validate-config</code> рекурсивно проверяет все <code>easyp.yaml</code>, <code>easyp.gen.yaml</code>, <code>protobuf.mod</code> и <code>protobuf.lock</code> внутри текущего каталога. Передайте <code>--cfg &lt;файл&gt;</code>, чтобы проверить один файл, или <code>--cfg &lt;каталог&gt;</code>, чтобы проверить другой каталог. В JSON-ошибках указан файл, а для ошибок структуры YAML — строка и столбец. Некорректная версия lock-файла, неполные записи и неверные хеши выдаются как ошибки проверки.

~~~bash
easyp validate-config
easyp validate-config --cfg ./services --format json
easyp validate-config --cfg ./services/api/easyp.gen.yaml
~~~

<code>mod vendor</code> проверяет зафиксированные Git-зависимости и копирует их <code>.proto</code> в <code>easyp_vendor</code> по import path. Старый каталог заменяется только после успешного копирования всех файлов. Совпадающие import path вызывают ошибку. При наличии локальных <code>replace</code> копируется эффективный граф локальных и проверенных удалённых исходников без изменения опубликованного lock.

<code>ls-files</code> показывает локальные <code>.proto</code> из корней <code>protobuf.mod</code>. По умолчанию команда также включает достижимые импорты из зависимостей и встроенных well-known proto, разрешая зависимости через v1 lock или локальные замены. <code>--include-imports=false</code> показывает только локальные файлы; вне frozen это пропускает разрешение зависимостей. В JSON есть поля <code>files</code>, <code>roots</code> и, при проблемах с импортами, <code>errors</code>.

<code>schema-gen --out-dir schemas</code> создаёт отдельные JSON Schema для <code>easyp.yaml</code>, <code>easyp.gen.yaml</code> и <code>protobuf.lock</code>: файлы с суффиксом <code>-v1.schema.json</code> и псевдонимы без версии. <code>protobuf.mod</code> — текстовый манифест; проверяйте его командой <code>validate-config</code>. CLI также проверяет семантические правила, не выраженные в JSON Schema.

Экспортируемый пакет <code>github.com/easyp-tech/easyp/mcp/easypconfig</code> регистрирует инструмент <code>easyp_config_describe</code> в MCP-сервере через <code>easypconfig.RegisterTool(server)</code>. Инструмент описывает два редактируемых YAML-файла и использует те же JSON Schema, что и <code>schema-gen</code>. Он не описывает <code>protobuf.mod</code> и <code>protobuf.lock</code>.

## Минимальный пример

~~~text
module github.com/acme/contracts
roots proto
require github.com/acme/shared v1.2.0
~~~

~~~yaml
# easyp.gen.yaml
version: v1
generate:
  modules: [github.com/acme/contracts]
plugins:
  - name: go
    out: ./gen/go
~~~

~~~yaml
# easyp.yaml
version: v1
linters:
  default: STANDARD
breaking:
  baseline: git:main
~~~

Точные поля и текущие ограничения описаны в справочниках по ссылкам выше.

## Ошибки и неинтерактивный запуск

<code>ls-files</code> сначала выводит полный JSON или текстовый результат, затем возвращает ненулевой код, если при обходе импортов обнаружена ошибка. Наличие массива <code>errors</code> не означает успешную проверку. <code>--include-imports=false</code> намеренно перечисляет только локальные файлы и не проверяет целостность импортов.

<code>init</code> не открывает скрытый управляющий терминал при перенаправленных вводе или выводе. Укажите <code>--module</code>, если идентификатор невозможно получить локально. Идентификатор по origin берётся из объявленного Git URL до транспортной подстановки <code>insteadOf</code>. Перезапись отличающегося существующего конфига требует подтверждения в терминале; ответ из pipe не принимается.

Синтаксис политики и поддерживаемые настройки проверяются и при исполнении команды, и в <code>validate-config</code>. Непустой breaking baseline должен начинаться с <code>git:</code>. Lint группирует файлы по действующей политике и модулю, сохраняя исключения отдельных файлов и порядок диагностики.
