---
title: "Package Manager"
description: "Resolve and lock Git-based protobuf dependencies in EasyP v1."
---

The v1 package manager reads `protobuf.mod` and writes `protobuf.lock`. It records each selected Git commit and an `h1:` content hash, then verifies the hash when downloading or reusing a cached module.

## Declare dependencies

```text
module github.com/acme/contracts
roots proto

require (
    github.com/acme/shared v1.2.0
    github.com/acme/weather v2.1.0
)
```

`roots` defaults to `.` when omitted. A requirement may omit its version: `mod tidy` resolves the Git repository's current HEAD and locks its exact commit. Repeating `tidy` keeps that commit; `mod update` refreshes versionless requirements to HEAD. You may instead give a SemVer tag or a full 40- or 64-character Git commit hash. `replace module => ../local-copy` points generation and linting at a local checkout. Remove local replacements before writing a reproducible lock with `mod tidy` or `mod update`.

For a Git repository with multiple `protobuf.mod` files, require each nested module separately by the identity declared in its manifest. For untagged modules, write `require repo/foo` and `require repo/bar`; EasyP finds both manifests and locks the resolved commits without module-specific tags. Explicit commit hashes stay pinned during `mod update`. Tagged releases remain optional: a module in `foo/` uses a tag such as `foo/v1.2.3`. EasyP resolves each module's source roots independently.

## Commands

| Command | Behavior |
|---------|----------|
| `easyp mod tidy` | Resolves direct and transitive requirements and writes `protobuf.lock` |
| `easyp mod download` | Downloads the exact commits in `protobuf.lock` and verifies their hashes |
| `easyp mod update` | Refreshes requirements within their current major versions, then updates the lock |
| `easyp mod vendor` | Verifies locked dependencies and copies their `.proto` files into `easyp_vendor` |

```bash
easyp mod tidy
easyp mod download
easyp mod vendor
easyp generate
```

Commit `protobuf.mod` and `protobuf.lock` for repeatable builds. The module cache is under `$HOME/.easyp/v1/git` by default; set `EASYPPATH` to change its parent directory. `mod vendor` requires the lock and rejects local replacements and duplicate import paths. The `easyp_vendor` directory is a copy of dependency sources, not a replacement for the lock.

## Dependencies using Buf or older EasyP

A Git dependency may declare its proto roots in `buf.work.yaml`, Buf v1 or v2 `buf.yaml`, or an older EasyP `easyp.yaml`. Older EasyP `protobuf.mod` requirements are also read transitively. If none of those files exists, its repository root is used. This compatibility applies to dependency metadata; the consuming project uses v1 `protobuf.mod`.

Buf Registry dependencies have no automatic Git identity. Declare the corresponding Git module in the consuming `protobuf.mod` when those imports are needed. Buf include/exclude filters are not supported as Git import roots and produce an explicit error.

See [`protobuf.mod`](/docs/reference/protobuf-mod) and [`protobuf.lock`](/docs/reference/protobuf-lock) for their field-level formats.
