---
title: "Package Manager"
description: "Resolve and lock Git-based protobuf dependencies in EasyP v1."
---

The v1 package manager reads <code>protobuf.mod</code> and writes <code>protobuf.lock</code>. It records each selected Git commit and an <code>h1:</code> content hash, then verifies the hash when downloading or reusing a cached module.

## Declare dependencies

~~~text
module github.com/acme/contracts
roots proto

require (
    github.com/acme/shared v1.2.0
    github.com/acme/weather/v2 v2.1.0
)
~~~

<code>roots</code> defaults to <code>.</code>. SemVer requirements select the maximum requested minimum. A full 40- or 64-hex-character commit specifies an exact revision. A tag and SHA are compatible when the selected tag resolves to that same commit; different commits conflict. SHA values are not ordered as SemVer by date or Git ancestry.

A versionless requirement adds no constraint when the graph supplies a SemVer or exact commit. Only a still-unconstrained requirement uses current HEAD on the first <code>mod tidy</code>; subsequent tidy runs preserve the lock pin, while <code>mod update</code> refreshes HEAD. Explicit commits stay pinned.

<code>replace module =&gt; ../local-copy</code> applies only from the main <code>protobuf.mod</code>, including to transitive requirements. All relative replacement paths use the main manifest directory; absolute paths are used directly. With <code>replace</code>, commands use a local effective graph and preserve <code>protobuf.lock</code> byte-for-byte; a missing lock is not created. <code>mod tidy</code> also leaves the manifest unchanged. <code>get</code> and <code>mod update</code> may edit explicit requirements without adding fork-only transitives. <code>mod download</code> installs only needed unreplaced snapshots. Remove replacements and run <code>mod tidy</code> to produce a publishable lock. See [local replacements](/docs/guides/debugging-replace).

For a Git repository with several manifests, require each nested module separately by its identity. For example, <code>require repo/foo</code> and <code>require repo/bar</code> need no module-specific tags if HEAD is suitable. A <code>v1.2.3</code> release of the module in <code>foo/</code> uses tag <code>foo/v1.2.3</code>. Each module's roots are resolved independently.

Module commands and <code>get</code> find the nearest ancestor <code>protobuf.mod</code> within the workspace. <code>easyp get &lt;module&gt;</code> adds a direct requirement; <code>@v1.2.3</code> or <code>@&lt;full-commit&gt;</code> selects a version. Without a suffix, the unconstrained-requirement rules above apply. Transitive requirements are added with <code>// indirect</code>, and repeated calls do not duplicate entries. Resolution errors leave the manifest and lock unchanged.

Major versions use Go-style identities: v0/v1 are unsuffixed; v2+ requires matching <code>/vN</code>. The <code>+incompatible</code> exception requires verified pre-native metadata; it never bypasses a native manifest. See [exact grammar and Git mapping](/docs/reference/protobuf-mod).

## Commands

| Command | Behavior |
|---------|----------|
| <code>easyp get &lt;module&gt;[@version&#124;@commit]</code> | Adds or promotes a direct requirement, resolves transitive requirements, and writes <code>protobuf.lock</code> |
| <code>easyp mod tidy</code> | Resolves direct and transitive requirements and writes <code>protobuf.lock</code> |
| <code>easyp mod download</code> | Downloads the exact commits in <code>protobuf.lock</code> and verifies their hashes |
| <code>easyp mod update</code> | Refreshes requirements within their current major versions, then updates the lock |
| <code>easyp mod vendor</code> | Verifies locked dependencies and copies their <code>.proto</code> files into <code>easyp_vendor</code> |

~~~bash
easyp get github.com/acme/contracts/proto/user
easyp mod vendor
easyp generate
~~~

Commit <code>protobuf.mod</code> and <code>protobuf.lock</code> for repeatable builds. The module cache is under <code>$HOME/.easyp/v1/git</code> by default; set <code>EASYPPATH</code> to change its parent directory. Without replacements, <code>mod vendor</code> uses the published lock. With replacements it snapshots the effective graph without writing that lock. Duplicate import paths are errors. The <code>easyp_vendor</code> directory is a copy of dependency sources, not a replacement for the lock.

## Immutable tags and cache reuse

<code>tidy</code>, <code>get</code>, and <code>update</code> verify each fetched previously locked SemVer against its recorded commit and hash. A republished tag raises <code>ErrLockedVersionChanged</code> before installing the new graph or writing the manifest or lock, including for transitive dependencies and warm caches. Selecting a new version and refreshing unconstrained HEAD requirements remain available.

<code>mod download</code> retrieves the locked commit even after a tag moves, if that commit remains available. Reused Git objects let known exact commits avoid remote access. A cold request first tries a depth-one fetch of the exact commit and falls back to reachable history when needed; it never substitutes HEAD. Tag lookups are refreshed separately, and installed contents remain hash-verified.

## Dependencies using Buf or older EasyP

A Git dependency may declare its proto roots in <code>buf.work.yaml</code>, Buf v1 or v2 <code>buf.yaml</code>, or an older EasyP <code>easyp.yaml</code>. Older EasyP <code>protobuf.mod</code> requirements are also read transitively. If none of those files exists, its repository root is used. This compatibility applies to dependency metadata; the consuming project uses v1 <code>protobuf.mod</code>.

When adapting an older <code>easyp.yaml</code>, both <code>deps</code> and generation Git inputs contribute requirements. Exact source/version duplicates are removed; different minimums remain visible to MVS, and malformed deps fail explicitly. A matching native <code>protobuf.mod</code> takes precedence. Only metadata is read; dependency plugins are never executed.

Buf Registry dependencies have no automatic Git identity. Declare the corresponding Git module in the consuming <code>protobuf.mod</code> when those imports are needed. Buf include/exclude filters are not supported as Git import roots and produce an explicit error.

See [<code>protobuf.mod</code>](/docs/reference/protobuf-mod) and [<code>protobuf.lock</code>](/docs/reference/protobuf-lock) for their field-level formats.

## Reachable imports and direct requirements

Before writing a new manifest or lock, <code>mod tidy</code> checks the import closure reachable from the local module, including imports inside dependency files. Missing files and invalid reachable protobuf syntax stop the operation. Unrelated files in a dependency are not all compiled or linted. An import under <code>google/protobuf/</code> must actually exist; the prefix alone does not make it a bundled file.

When a local source starts importing a previously indirect module, <code>tidy</code> removes the existing <code>// indirect</code> marker while preserving its version and unrelated comments. This does not discover an arbitrary Git repository from an unknown proto path. Registry-specific Buf dependency identities still require explicit Git mapping and are not silently converted into repository URLs.

## Frozen builds

Commit <code>protobuf.mod</code> and <code>protobuf.lock</code>, then opt into <code>--frozen</code> explicitly. Even a module with no dependencies needs an empty lock; a source directory without a native manifest is rejected. <code>CI=true</code> does not enable this mode.

~~~bash
# Prepare and review the lock outside frozen mode
easyp mod tidy
# Use the committed graph; exact-commit cache fills are allowed
easyp mod download --frozen
easyp --frozen generate
easyp mod --frozen vendor
~~~

Global, <code>mod</code>-level, and leaf-command placement are supported. A true value anywhere in the command lineage stays enabled even if a child passes <code>--frozen=false</code>. See [all supported placements](/docs/cli/configuration#explicit-frozen-mode).

Frozen rejects every root <code>replace</code> before accessing its path or fetching dependencies, including unused replacements. It verifies the manifest's direct requirements and the locked modules' transitive requirements; missing, invalid, incomplete, or stale locks fail instead of being repaired. Dependencies selected by identity use the consumer's manifest and lock and do not need their own lock files. Explicit workspace-relative generation module paths instead use the selected native module's manifest and lock; a generator-only directory needs no separate pair. Dependency-local replacement directives remain ignored.

There is no dependency re-resolution, HEAD/tag lookup, or manifest/lock creation or rewriting. Missing cache entries may be fetched at their exact locked commits. Content hashes are verified on cold and warm caches; corrupted installed contents fail rather than silently replacing the recorded hash. Frozen is not offline, and remote plugins can still need network access.

<code>mod download</code> installs the verified graph. <code>mod vendor</code> validates it before writing <code>easyp_vendor</code>. <code>mod tidy</code>, <code>get</code>, <code>mod update</code>, <code>init</code>, and <code>migrate</code> refuse frozen execution, including migration preview. Remove replacements and prepare the manifest/lock outside frozen mode. The normal local replacement and vendor behavior above is unchanged.

## Cache and revision-access errors

A hash mismatch in an installed module identifies the exact cache directory. Preserve it for investigation or quarantine only that entry, then retry <code>easyp mod download</code>. Do not rewrite <code>protobuf.lock</code> to hide the mismatch; the command does not automatically delete or repair the cache.

An inaccessible Git repository is not evidence that a tag is absent. If history was fetched but the pinned commit is unavailable, restore access to the original revision instead of substituting HEAD. Tag revalidation and integrity checks remain enabled; no automatic offline fallback is introduced.
